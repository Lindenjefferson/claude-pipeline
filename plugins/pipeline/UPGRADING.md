# Notas de atualização do plugin `pipeline`

Vão junto com cada versão instalada, para a skill `atualizar` lê-las no projeto. Termine a entrega em andamento, ou pause-a, antes de atualizar o plugin (a skill `atualizar` confere). Ao pular versões, leia as notas de cada uma, da mais antiga para a mais nova.

**A numeração voltou para 1.x.** O plugin nasceu na 2.0.0 e nunca quebrou compatibilidade, então o 2 nunca foi ganho: a 2.12.0 passou a ser a **1.12.0**, e cada versão anterior segue a mesma conta (a 2.9.9 é a 1.9.9, e assim por diante). Nada muda no comportamento. Uma cópia 2.x se atualiza pelo caminho normal — `claude plugin marketplace update linden-plugins` e `claude plugin update pipeline@linden-plugins --scope <escopo>`, depois `/reload-plugins` — porque o instalador compara com o que o marketplace oferece, não a ordem dos números; a skill `atualizar` continua valendo. Conferido na prática, de 2.12.0 para 1.12.0.

- **1.12.1**: nada muda no comportamento. Corrige a nota da renumeração acima, que mandava remover e instalar de novo: a atualização de 2.x para 1.x funciona pelo caminho normal.
- **1.12.0**: lê os ledgers da 1.11.0 e nada muda nos arquivos do projeto. O `dev` passa a commitar o teste que falha num commit só de arquivos de teste, antes do commit da implementação, e o `gate.py` avisa (sem mudar o veredito) quando o teste de um critério `AC-` apareceu primeiro num commit que mudou código junto. O aviso só sai em projeto com a linha "Arquivos de teste" de "Comandos" preenchida; sem ela não há como separar teste de código, e a checagem é pulada. Numa entrega em andamento, os commits já feitos não são refeitos: o aviso vai aparecer para os critérios que vierem junto com o código, e isso é informação, não bloqueio.
- **1.11.0**: lê os ledgers da 1.10.1 e nada muda nos arquivos do projeto. O guard dos comandos passa a valer também para a ferramenta PowerShell da sessão principal, lida com as regras do PowerShell: o que já era negado no Bash (pular o `pre-commit`, chegar à branch principal no modo autônomo, servidor de dev no primeiro plano) passa a ser negado ali também, e uma mensagem de commit que só *menciona* um flag continua passando. Depois do `/reload-plugins`, uma sessão aberta já usa o matcher novo. As regras de permissão nomeiam a ferramenta, então num projeto que já rodou o kickoff peça "atualizar o plugin" ou rode o passo 7 dele de novo: cada regra `Bash(...)` do `deny` e do `ask` ganha a gêmea `PowerShell(...)`. No fluxo, o passo 3 passa a oferecer, dentro do ✋ 1, preencher a seção "Execução em paralelo" do `CLAUDE.md` quando o plano tem tarefas que poderiam rodar juntas e a seção está vazia — responda e o manager a escreve; sem resposta, as tarefas rodam uma de cada vez, como antes.
- **1.10.1**: lê os ledgers da 1.10.0 e nada muda nos arquivos do projeto. A faixa de andamento passa a abrir com uma linha em branco, para a primeira linha não se misturar com o que o terminal imprimiu acima dela, e uma linha mais larga que o terminal dá uma linha a cada parte em vez de quebrar no meio; depois do `/reload-plugins`, uma sessão aberta já desenha assim. No fluxo, uma mudança de tela que você pede no checkpoint ou na revisão visual passa a atualizar também o mockup em `docs/mockups/<slug>.html`, no mesmo commit do briefing da correção: numa entrega com tela em andamento, o mockup pode estar desatualizado em relação ao que você já pediu, e a primeira mudança de tela depois da atualização o põe em dia.
- **1.10.0**: lê os ledgers da 1.9.9, e nada muda nos arquivos que o projeto já tem. O que muda é daqui para a frente: a rodada de design grava o mockup em `docs/mockups/<slug>.html`, versionado, em vez de `.superpowers/design/<slug>/`; a spec vai para `docs/specs/<slug>.md` e o plano para `docs/plans/<slug>.md`, os três com o mesmo slug da entrega. O `gate.py` ganha a checagem `Artifacts` e recusa um plano que aponte para dentro de `.superpowers/`: num plano que cite esse caminho, mova o arquivo citado para um caminho versionado e corrija a linha. Um mockup que já esteja em `.superpowers/design/` continua lá; mova-o para `docs/mockups/` para ele ir junto no clone. Um projeto que já usa outros caminhos para spec e plano continua funcionando — o que o gate rastreia é o caminho registrado no ledger. O gate também deixa de contar como critério um id seguido de `<` ou `{`, que é o modelo do id e não um critério (ele avisa nomeando cada um): um plano que escreve `AC-T<tarefa>-<n>` para explicar o formato deixa de barrar o merge, e quem contornou isso reescrevendo o modelo sem o hífen pode escrevê-lo como quiser.
- **1.9.9**: lê os ledgers da 1.9.8, que continuam dando as mesmas métricas: cada linha de `measure` gravada por esta versão nomeia a execução que completa, e as linhas das versões anteriores, que não nomeiam, seguem completando a última execução daquele agente, como completavam. Numa entrega em andamento nada precisa ser refeito; um tempo que já tenha caído na execução errada continua lá. O que muda é daqui para a frente: com mais de uma execução daquele agente sem medida, o `ledger.py measure` recusa e lista o `at` de cada uma, e o manager passa `--at <at>` para dizer qual a notificação completa. O mod deixa de pedir a retomada de uma entrega pausada esperando a janela de uso — quem retoma é o manager, dormindo a espera num comando em background, como já fazia; a notificação de que a entrega precisa de você continua. Depois do `/reload-plugins`, uma sessão aberta já segue o novo comportamento.
- **1.9.8**: lê os ledgers da 1.9.7; nada muda nos arquivos do projeto. O mod passa a fazer duas coisas por conta: uma notificação do sistema quando a entrega precisa de você (gate pronto, o manager perguntando ou parando, um VALIDAR novo), uma vez por estado (a retomada automática que esta versão trouxe saiu na 1.9.9). O `/andamento` ganha um botão por agente em andamento, que abre a conversa dele, e a lista dos arquivos da entrega. Depois do `/reload-plugins`, uma sessão aberta já recebe o aviso.
- **1.9.7**: lê os ledgers da 1.9.6; nada muda nos arquivos do projeto. O manager passa a despachar a tarefa seguinte assim que o relatório do agente chega, sem esperar a notificação de término, e `--seconds`/`--tokens` ficam opcionais; quando a notificação chega depois do `add`, o `ledger.py measure --agent <agente> [--task <id>] --seconds <d> --tokens <n>` completa aquela execução, numa linha nova do ledger. Numa entrega em andamento, nada precisa ser refeito: execuções já registradas sem os números continuam valendo, e o `elapsed` de cada ciclo passa a contar o horário delas. O kickoff passa a oferecer remover a cópia `local` de um plugin já habilitado no escopo `user` (nunca a `project`) e, numa máquina nova, pula a extensão já habilitada em qualquer escopo.
- **1.9.6**: lê os ledgers da 1.9.5; nada muda nos arquivos do projeto. A faixa de andamento passa a ter até três linhas; uma sessão aberta mostra a nova depois do `/reload-plugins`.
- **1.9.5**: lê os ledgers da 1.9.4. O plugin declara uma dependência nova, `claude-code-setup@claude-plugins-official`, que o Claude Code instala sozinho com a atualização e o `/reload-plugins`; ela só é usada num projeto novo. A seção "Preparar uma máquina" ganha a linha "Extensões do Claude Code", que o kickoff acrescenta: liste nela as extensões que o projeto usa.
- **1.9.4**: lê os ledgers da 1.9.3 (um `add` sem `diff` conta como não medido). O `dev` pode devolver uma tarefa como `NEEDS_CONTEXT` marcado `simpler:` (o manager o registra com `add --simpler`), que o manager responde com uma linha da Errata ou leva ao usuário; o `claim` passa a gravar o head do despacho, e um `claim` antigo sem ele mede o diff como antes. Nada muda nos arquivos do projeto.
