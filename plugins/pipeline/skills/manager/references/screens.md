# Screens: design round, design review, visual checkpoint and visual review

Read when a task or a fix creates, redesigns or changes a screen, before dispatching it (and before step 3 when planned). Each part names the step it belongs to; the screen formats are those the Rules say.
- **Design round** (step 3; the request creates or redesigns a screen; not a fix that keeps the layout): before drafting the plan, load the `frontend-design` skill (the kickoff checks it is installed; if it is missing, follow these steps without it), plus a data-visualization skill when the screen has charts, highlight numbers or a dashboard and one is installed. Produce one comparison page: each new or redesigned screen in every screen format the project's `CLAUDE.md` lists, in every theme the project has, with realistic sample data (never real data), saved and committed as `docs/mockups/<slug>.html`, one self-contained page under the delivery's slug, like its spec and plan (never in `.superpowers/`, which the kickoff ignores: the gate refuses a plan that points there). Its decisions are plan input: color tokens (each with its value in each theme and its measured contrast), layout rules per screen format, and the mock, which every UI task names. A screen change the user asks for later, at the visual checkpoint or the visual review, updates this mock the same way, with the skill, in the same commit as the `fix-N` brief and before you dispatch it: the mock is the agreed picture of the screen, and a stale one makes the design review report differences the user has already decided.
- **Design review** (step 4.2; cycles with a screen that has a mock): when qa reports, before you `add` its verdict, compare each of qa's captures with its mock, yourself with the `frontend-design` skill or through a subagent that has the Skill tool (`dev`, `qa` and `reviewer` have none: brief them for a skill's result, never to load it): what the eye reads first, spacing and alignment, how each screen format uses its space, the color tokens. Each difference is a finding of qa's run, appended to its report file, with the capture and the mock as evidence: Important when it changes what the eye reads first or breaks a screen format, Minor otherwise, origin `execution`; an Important one makes qa's verdict FAIL, so `status` asks for the fix and the re-run. A mock with no captures (the product does not run here) is a `note --validar`.
- **Visual checkpoint** (step 4.4; cycles with screens). Show the user qa's captures and recording, one line per screen, and continue. It does not stop the cycle: what the user asks to change becomes a `fix-N` task, or a product decision for the plan's next cycle.
- **Visual review** (step 7, approval 2; mandatory when the delivery has screens): show the captures of every new or changed screen of the whole delivery (in every screen format) and the recording of the main flow, and wait until the user has seen them; a change the user asks for goes back as a `fix-N` task and through the gate again.
