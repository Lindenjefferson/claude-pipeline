# Screens: design round, design review, visual checkpoint and visual review

Read when a task creates, redesigns or changes a screen, before step 3 (small work: before step 4). Each part names the step it belongs to.

- **Screen formats** are those the project's `CLAUDE.md` lists. A delivery with screens and none listed: ask the user before the design round (or the first cycle) and write them on that line.
- **Design round** (step 3; the request creates or redesigns a screen; not a fix that keeps the layout): before drafting the plan, load the `frontend-design` skill (the kickoff checks it is installed; if it is missing, follow these steps without it), plus a data-visualization skill when the screen has charts, highlight numbers or a dashboard and one is installed. Produce one comparison page: each new or redesigned screen in every screen format the project's `CLAUDE.md` lists, in every theme the project has, with realistic sample data (never real data), saved in `.superpowers/design/<slug>/`. Its decisions are plan input: color tokens (each with its value in each theme and its measured contrast), layout rules per screen format, and the mock, which every UI task names.
- **Design review** (step 4.2; cycles with a screen that has a mock): when qa reports, before you `add` its verdict, compare each of qa's captures with its mock, yourself with the `frontend-design` skill or through a subagent that has the Skill tool (`dev`, `qa` and `reviewer` have none: brief them for a skill's result, never to load it): what the eye reads first, spacing and alignment, how each screen format uses its space, the color tokens. Each difference is a finding of qa's run, appended to its report file, with the capture and the mock as evidence: Important when it changes what the eye reads first or breaks a screen format, Minor otherwise, origin `execution`; an Important one makes qa's verdict FAIL, so `status` asks for the fix and the re-run. A mock with no captures (the product does not run here) is a `note --validar`. In the re-runs of a fix round (step 4.3), the design review runs again on qa's new captures of the screens the fix touched.
- **Visual checkpoint** (step 4.4; cycles with screens). Show the user qa's captures and recording, one line per screen, and continue. It does not stop the cycle: what the user asks to change becomes a `fix-N` task, or a product decision for the plan's next cycle.
- **Visual review** (step 7, approval 2; mandatory when the delivery has screens): show the captures of every new or changed screen of the whole delivery (in every screen format) and the recording of the main flow, and wait until the user has seen them; a change the user asks for goes back as a `fix-N` task and through the gate again.
