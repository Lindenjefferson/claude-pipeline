# Parallel execution: worktrees, waves and integration

Read when the project's `CLAUDE.md` has the "Execução em paralelo" section, before any dispatch or integration of step 4, and again after a compaction or a resumed session. Each part names the step it belongs to.

- **In parallel** (step 4.1): dispatch at once every task whose dependencies are integrated and whose `Touches:` (as the Errata leaves them, module docs aside) share nothing with another running task. Create each worktree yourself, in `../_temp/<project>-worktrees/` (the `_temp` folder next to the project, created when missing, for the work in progress the user deletes later), from the current head and prepare and check it before dispatching, one at a time, as that section says (dependencies, environment file, per-copy port and data store, then the check that each runs; the agent's isolation may refuse those commands), and dispatch the `dev` without the agent tool's own worktree isolation. The brief gives the worktree path, its origin commit and the main worktree's paths of the plan and of any mock (git-ignored files such as `.superpowers/` are not in a task worktree). Verification that uses a resource the section lists as shared, or a data store it does not isolate per copy, runs one task at a time.
- **Integrate** (step 4.1) a task once its agent is finished as step 4.1 says (a live agent still locks its worktree). Integrate in plan order (fast-forward, or cherry-pick the task's commits; a merge commit is only for a front, so the gate sees every task commit), one command at a time: integrate, `add` to the ledger, then tear the copy down as that section says, check that nothing of it still listens, and remove the worktree. A conflict only in module docs (every file `git diff --name-only --diff-filter=U` lists is an `NN-*.md` under `docs/modulos/`): merge both sides yourself and continue the integration. Any other conflict: abort the integration, and the `dev` rebases the task in its worktree onto the delivery head, the brief's new origin commit. A red test after integrating goes back to the `dev`: before the `add`, in the same worktree; after it, as a `fix-N` on the delivery branch.
- **Fix round and next cycle** (step 4.3): a large round may be split into parallel `fix-N` tasks as in step 4.1; a shared helper or component a finding asks for has one owner task, named in the other briefs, which use it only once it is integrated. While the round runs, a task of the next cycle whose dependencies are integrated and whose `Touches:` share nothing with the round may start as in step 4.1; integrate and `add` it, whatever its verdict, only once this cycle closes (the ledger refuses it before).
