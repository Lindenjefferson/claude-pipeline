# Autonomous mode

Read when the user turns autonomous mode on (for example before leaving), recorded with `mode autonomous`, or when `status` shows the mode is autonomous. Only then:
- **The time the user is back.** When they turn it on, ask (`AskUserQuestion`) whether they want to set the time they are back; with one, `mode autonomous --until <HH:MM>`. While it is set, `status` names each run that no longer fits before it: do not dispatch it, and dispatch what still fits. When `status` says the night is over, stop what runs and `pause` as `pause.md` says, its text the morning summary (what was done since the time was set, as `status` counts it, the VALIDAR items waiting, the next step), then delete the heartbeat and send the `PushNotification`.
- **Heartbeat.** Create a recurring job of this session with `CronCreate` (every 15 minutes, off the :00 and :30 marks) whose prompt is "pipeline heartbeat: run `ledger.py status --tick` and continue the delivery", so a report that arrived without its completion notification never leaves the delivery idle. Create it only when `CronList` shows none. Delete it with `CronDelete` on `mode supervised` and when nothing more can move without the user (the gate READY on the last delivery the user queued, the delivery stopped with `note --validar`, or the night over); a resource pause (`pause.md`) is not such a stop. On a resumed session in autonomous mode, check `CronList` and create it again if it is gone; it lives only in this session and expires after 7 days.
- **A resource runs out**: the resource pause of `pause.md`, which keeps the heartbeat.
- Approval 1 becomes the plan reviewer's PASS, or the waiver `status` says; the plan's product decisions and the design page are also `note --validar`.
- Never merge into the default branch, push or deploy, unless the user gave a standing approval (`approve --until <x.y.z> --conditions <their words>`): it also covers the security scan of a sensitive delivery (`references/security.md`); then, once the gate is READY, its report committed and the conditions checked, merge and push that delivery in autonomous mode. Run git through the Bash tool, where the plugin's hook denies merging into and pushing the default branch while the ledger is in autonomous mode, except the gated tree a standing approval covers. A push of the work branch passes the hook, so leave it for the user's return too: nothing leaves the machine while they are away. The next delivery starts on a branch stacked on this one (`git switch -c <branch>` from its head, then `start --slug <slug> --archive --base <this branch>`, which promotes its preparation when it began with `--next` and `mode autonomous` again, since a new ledger starts supervised); its gate takes the base from the ledger.
- When the user is back: `mode supervised` (and `resume` if the night paused the delivery), then finish step 6 (the security scan `status` still asks for, and the gate) and run approval 2 (step 7, VALIDAR included) for each delivery, oldest first. For an earlier delivery, switch to its branch and pass `--ledger .superpowers/ledger-<its slug>.jsonl` to `gate.py` and to `ledger.py` (before its command), starting with `mode supervised`; a fix made there is merged into the stacked branch.
