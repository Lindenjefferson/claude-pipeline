---
name: manager
description: Use when asked to develop, implement, or deliver a module, feature, or bug fix in a personal project where the `pipeline` plugin is enabled (`claude plugin install pipeline@linden-plugins --scope local`). Runs the delivery in short cycles (dev per task, independent tasks in parallel; then reviewer and qa in parallel over the cycle; then a local gate script) with two user approvals, so nothing wrong leaves the machine. Triggers on "manager", "desenvolver módulo", "implementar módulo", "nova feature", "corrigir bug", "deliver".

# Manager

The main session is the manager: it plans, dispatches agents by name (`pipeline:dev`, `pipeline:reviewer`, `pipeline:qa`, `pipeline:discovery`), integrates their work, sends findings back to the `dev`, keeps the ledger, and never writes product code itself.

Two moments stop for the user: **approving the plan** and **approving the merge/push**. Between them the user is asked only product decisions; everything else runs without stopping. In autonomous mode (below) neither stops, and nothing reaches the default branch.

## Ledger
`.superpowers/ledger.jsonl` (git-ignored), written only with `sh "${CLAUDE_PLUGIN_ROOT}/hooks/python.sh" "${CLAUDE_PLUGIN_ROOT}/skills/manager/ledger.py" <command>` (its docstring has the exact rules; run from a task worktree, it finds the main worktree's ledger):
- `start --slug <slug> --base <default-branch>` once, in step 1, when the delivery branch is created. If the ledger still holds an earlier delivery, add `--archive`. `plan --path <plan path>` when the plan is approved (step 3; none for small work).
- `claim --task <id>` when you dispatch a `dev` (it refuses a task already in flight or done; `status` lists what is in flight, and `release --task <id>` frees a run that was lost). The `add` below frees the claim.
- `add --agent dev --task <id> --verdict <verdict> --seconds <duration> --tokens <n>` after each task. A fix round always uses the id `fix-N` and the cleanup step the id `cleanup`.
- `add --agent reviewer|qa --verdict PASS|FAIL --critical <n> --important <n> --minor <n> --origin <origin>=<n>,... --report <path> --seconds <duration> --tokens <n>` after each pass, with the counts and finding origins of its report (defined in the report section of `agents/reviewer.md`) and the file you saved the report in. With `--task spec|plan`, one round of that review loop (steps 2 and 3).
- `--seconds` and `--tokens` come from the agent's completion notification; without it (step 4.1), leave both out: never estimate.
- `note --text '<text>'` for every decision you take on the user's behalf (a finding you rule out, a check you skip); add `--validar` when the user must confirm it on return (every product decision and every approval you take in autonomous mode); the `validar` skill walks those with the user.
- `waive --agent reviewer|qa [--task spec|plan] --reason '<text>'` when the open findings of that agent's latest FAIL will not be fixed: you ruled them all out, or the user accepted them. It is the only way past such a FAIL; never record a PASS the agent did not give. `extend --reason '<text>'` when `status` asked or stopped after the fix rounds and the user decides the fixes go on: one more round.
- `mode autonomous` when the user turns autonomous mode on, `mode supervised` when they are back; `status` shows the mode.
- `defer --text '<text>'` for every item left for later (a Minor not fixed now, a quarantined test, a follow-up); `resolve --id <id> --decision '<text>'` records your final decision on it: `fixed in <task>`, `discarded: <reason>` or `moved to <named later delivery>: <reason>`.
- `lesson --text '<rule>' [--check <test, helper or lint rule>]` for every lesson of step 4.5.
- `status` shows the current cycle and what it still needs. Read progress back from it after a compacted context; keep no other progress log. A claim whose agent is no longer running: its commits already on the delivery branch, `add` it; still in its worktree, integrate it; no commits, `release` it.
- Notes, waivers, deferred items, decisions and lessons are copied into the committed quality report: write them as versioned text, under the project's rules for versioned files (no path to local or private material, no real data).

## 0. Size the work
State the tier in one line so the user can override it. Anything touching auth, permissions, sessions, secrets, schema/migrations/access rules, or writes to money or other sensitive data is at least **standard**, and so is anything that creates or redesigns a screen.

| Tier | Looks like | Steps |
|---|---|---|
| small | 1–3 files, obvious change, no new contract | 1 → 4 (one task, no written plan) → 6 → 7 |
| standard | a few files, one real design choice | 1 → 3 → 4 → 5 → 6 → 7 |
| large | new module, open questions, a spec to write | 1 → 2 → 3 → 4 → 5 → 6 → 7 |

For a bug fix, the first task is a test that reproduces the bug and fails; use `superpowers:systematic-debugging` to find the cause.

## Steps
1. **Branch.** From a clean tree on the default branch: `git switch -c <feat|fix>/<slug>`, then ledger `start` (and `mode autonomous` if the user turned it on). The spec, the plan and everything after them are committed on this branch, never on the default one.
2. **Spec** (large only). Raw sources to mine (spreadsheets, reference apps, documents): dispatch `discovery` first. Then `superpowers:brainstorming`, pointing it at `${CLAUDE_PLUGIN_ROOT}/skills/manager/templates/spec-checklist.md`. If the spec touches a sensitive domain (step 0), tell brainstorming to skip its builder check, then dispatch `reviewer` in **spec mode**, which covers it, and run the review loop of step 3; product decisions go to the user. Commit the spec.
3. **Plan** (standard and large). Read the project's `docs/lessons.md` first, then `superpowers:writing-plans`, or a subagent with the same brief (spec path, lessons, the rules of this step) to draft a long plan without spending your context; you apply the product decisions. Thin vertical slices grouped in **cycles of at most about 6 tasks**.
   - **Design round** (the request creates or redesigns a screen; not a fix that keeps the layout): before drafting the plan, load the `frontend-design` skill (the kickoff checks it is installed; if it is missing, follow these steps without it), plus a data-visualization skill when the screen has charts, highlight numbers or a dashboard and one is installed. Produce one comparison page: each new or redesigned screen in every screen format the project's `CLAUDE.md` lists, in every theme the project has, with realistic sample data (never real data), saved in `.superpowers/design/<slug>/`. Its decisions are plan input: color tokens (each with its value in each theme and its measured contrast), layout rules per screen format, and the mock, which every UI task names.
   - **Each task** has an id, `Goal:` (one line: the spec item it serves and what the user gets from it), `Depends on:` (task ids, or none), `Touches:` (the files and shared resources it changes: schema, a migration number, a config file, a seed), and its acceptance criteria.
   - **Pre-mortem.** For every write operation (as section 1 of the spec checklist defines it), answer that section's questionnaire (or point to the spec's answers); each answer becomes acceptance criteria, positive and negative, abuse cases included.
   - **Criteria** are written as Given/When/Then, each with an id `AC-<task>-<n>` (for example `AC-T3-2`), and become the names of the tests that prove them (the id first; `_` for `-` and `.` where test names are identifiers). The gate fails when a criterion id of the plan appears in no test file.
   - **Assumptions**: section 2 of the spec checklist. An unproven one does not go into the plan as code; it goes to the user or becomes a spike task.
   - **Checked against the code.** Every "already exists" (function, component, table, helper) is verified by a search, with its path; every sequential number (migrations, ids) is reserved in the plan per task, after the highest one in the code.
   - **Granularity.** Full code only for pure rules (calculations, validations) and for migrations and the data layer, where the exact text is the decision. UI and wiring tasks carry the interfaces they expose or consume, the criteria and the tests that prove them; the `dev` follows the patterns already in the code.
   - **Invariants and layout.** Each item of Invariants and of Web and UI in the general checklist that the plan touches gets its task and its test (the data-layer enforcement, the lock and its two-session test, the layout check with the project's numbers).
   - **New dependencies** each carry a justification (why, the alternative without it, who maintains it).
   - **Product decisions** the plan takes on the user's behalf (a default, a limit, an allowed or refused case) are listed in a `## Product decisions` section.
   - End the plan with an empty `## Errata` section.
   - **Plan review.** Dispatch `reviewer` in **plan mode** on the plan and run the review loop.
   - **Review loop** (spec and plan): record each round with `add --task spec|plan` and its report file, apply the reviewer's Critical and Important corrections, take product questions to the user, and dispatch it again on the corrections until PASS. `status` says when to ask the user instead (`waive` what the user accepts) and, in autonomous mode, what the last round checks and when to stop.
   **Approval 1: show the plan, its product decisions, the design page when there is one and the reviewer's verdict, and wait for the user.** Commit the plan and record it with `plan --path`, then each of its cycles, in plan order, with `scope --cycle <name> --tasks <ids>`; record a cycle again whenever the plan changes it (an errata, a cycle added), so the progress line says how many tasks and cycles are left.
4. **Cycle**, repeated for each group of tasks in the plan; `status` gives its `<from>`, the commit its diff starts at.
   1. **Tasks.** `claim` the task, then dispatch the `dev` with a brief naming the plan path and the task id and telling it to read the plan's `## Errata` first (for small work, the request and its acceptance criteria).
      - **In parallel** when the project's `CLAUDE.md` has the "Execução em paralelo" section: dispatch at once every task whose dependencies are integrated and whose `Touches:` (as the Errata leaves them) share nothing with another running task. Create each worktree yourself, in one folder next to the project named `<project>-worktrees`, from the current head and prepare and check it before dispatching, one at a time, as that section says (dependencies, environment file, per-copy port and data store, then the check that each runs; the agent's isolation may refuse those commands), and dispatch the `dev` without the agent tool's own worktree isolation. The brief gives the worktree path, its origin commit and the main worktree's paths of the plan and of any mock (git-ignored files such as `.superpowers/` are not in a task worktree). Verification that uses a resource the section lists as shared, or a data store it does not isolate per copy, runs one task at a time. Without that section, run tasks one at a time.
      - **Size each wave** before dispatching it: check the free memory and disk, and dispatch only the copies that fit while one more copy's peak stays free, at the per-copy peak `CLAUDE.local.md` gives (in the main worktree, the first that `git worktree list` prints; with no number there, measure the drop in free memory while the first copy is prepared and verified). The peak is preparing (installing, building, starting a data store) or verifying (a build, the test suite), not coding. The rest go as earlier ones finish.
      - **Check the report** before integrating: its `Tests:` line names the report's `Commit:` and has counts with nothing failing, `Mutation evidence:` names the guard loosened and the test that went red, or why there is no guard, and, for a screen with a mock, `Mock:` names the formats compared. A missing verdict, counts or evidence, another commit, a failure the task caused, NEEDS_CONTEXT or BLOCKED: the task goes back to the `dev` in the same worktree with what it lacked (NEEDS_CONTEXT or BLOCKED: `add` that verdict and `claim` it again; otherwise its claim stays until the `add`), never on to qa; a product question goes to the user (autonomous mode: decide and `note --validar`), and a resource that ran out is the pause of autonomous mode. A failure that fails at the origin commit too is not the task's: `defer` it or make it a `fix-N`, and integrate. A DONE_WITH_CONCERNS concern goes into the reviewer's brief.
      - **Integrate** a task after its agent's completion notification (a live agent still locks its worktree), or as soon as its report is in and its worktree is idle (`git status` shows nothing but ignored files and nothing listens on the copy's port): then stop the agent with `TaskStop` and integrate. The same holds for a `qa` that reported and is still running. Integrate in plan order (fast-forward, or cherry-pick the task's commits; a merge commit is only for a front, so the gate sees every task commit), one command at a time: integrate, `add` to the ledger, then tear the copy down as that section says, check that nothing of it still listens, and remove the worktree. A conflict: abort the integration, and the `dev` rebases the task in its worktree onto the delivery head, the brief's new origin commit. A red test after integrating goes back to the `dev`: before the `add`, in the same worktree; after it, as a `fix-N` on the delivery branch.
      **Errata.** When the code legitimately diverges from the plan (a renumbered migration, a changed test count, a pattern the code adopted that later tasks must follow), append one dated line to the plan's `## Errata` instead of repeating the correction in every brief, and commit it with the cycle. Errata is the only part of the plan you edit after approval; a change of scope or decision goes to the user.
   2. **Review and qa, in parallel**, both on `<from>..HEAD` (the integrated diff): `reviewer` once, and `qa` once with the acceptance criteria of the cycle's tasks and the delivery slug. The `qa` brief names a test output folder of its own (the per-run folder of "Execução em paralelo"). Save each report as it arrives in `.superpowers/reports/<slug>/<cycle>-<agent>-<n>.md` and `add` its verdict with `--report` naming that file.
      - **Design review** (cycles with a screen that has a mock): when qa reports, before you `add` its verdict, compare each of qa's captures with its mock, yourself with the `frontend-design` skill or through a subagent that has the Skill tool (`dev`, `qa` and `reviewer` have none: brief them for a skill's result, never to load it): what the eye reads first, spacing and alignment, how each screen format uses its space, the color tokens. Each difference is a finding of qa's run, appended to its report file, with the capture and the mock as evidence: Important when it changes what the eye reads first or breaks a screen format, Minor otherwise, origin `execution`; an Important one makes qa's verdict FAIL, so `status` asks for the fix and the re-run. A mock with no captures (the product does not run here) is a `note --validar`.
   3. **One fix round**, after both report. Send the `dev` one brief, as task `fix-N` (it stays in this cycle), naming the report files (absolute paths), the Minors worth fixing now (`defer` the rest) and the findings you ruled out. A large round may be split into parallel `fix-N` tasks as in step 4.1; a shared helper or component a finding asks for has one owner task, named in the other briefs, which use it only once it is integrated. While the round runs, a task of the next cycle whose dependencies are integrated and whose `Touches:` share nothing with the round may start as in step 4.1; integrate and `add` it only once this cycle closes (the ledger refuses it before). When a finding is wrong, `note` your ruling instead of sending it; when that leaves a FAIL with nothing to fix, `waive` it. After the fix, run the `reviewer` on the fix commits only (`<head it reviewed>..HEAD`), its brief naming its report file and the findings you ruled out so it does not report them again, and `qa` on the scenarios that failed or that the fix touched, in parallel (with the design review again on qa's new captures of the screens the fix touched); `status` says which are due. What still fails after this round: `status` says what comes next.
   4. **Visual checkpoint** (cycles with screens). Show the user qa's captures and recording, one line per screen, and continue. It does not stop the cycle: what the user asks to change becomes a `fix-N` task, or a product decision for the plan's next cycle.
   5. **Lessons.** For each Critical or Important finding that a rule would have prevented, and each lesson a `dev` report proposes, first ask **"can this be a check?"**: a test, a test helper or a lint rule that fails on the mistake. If yes, it goes to the `dev` with the fix round (or as a `fix-N` task); only what cannot be automated becomes one imperative line in the project's `docs/lessons.md`, with the paths it applies to, which you write and commit with the cycle. Record each one with `lesson`. A lesson broken a second time becomes a check in the same round, with no second chance as text.
5. **Cleanup** (standard and large). After the last cycle closes, one `dev` task `cleanup`: refactoring only (dead code, duplication, files grown too large), no behavior change. The `reviewer` checks its diff.
6. **Gate.** When the work touches a sensitive domain (step 0), run the `security-review` skill (the tool's native security review) once over the delivery branch; each finding goes to the `dev` as a `fix-N` task or is deferred with a decision, like the reviewer's. Before running the gate, decide every open deferred item yourself (`status` lists them) and `resolve` each: fixed (as a `fix-N` task), discarded, or moved to a named later delivery, always with the reason. In supervised mode, run the `validar` skill on the VALIDAR items still waiting before the gate, so the report carries the user's decisions. When `status` says ready: `sh "${CLAUDE_PLUGIN_ROOT}/hooks/python.sh" "${CLAUDE_PLUGIN_ROOT}/skills/manager/gate.py" --report <slug>` (its docstring lists the checks), in the Bash tool's background mode (a foreground call times out first). NOT READY: send the failing items to the `dev` as a `fix-N` task of the cycle and run the reviewer on that fix; the same check NOT READY a second time goes to the user (in autonomous mode, stop the delivery with it as `note --validar`). READY: it staged the quality report; commit it (`docs: quality report`).
7. **Close. Approval 2:** first the **visual review**, mandatory when the delivery has screens: show the captures of every new or changed screen of the whole delivery (in every screen format) and the recording of the main flow, and wait until the user has seen them; a change the user asks for goes back as a `fix-N` task and through the gate again. Then show the gate output, the ledger notes, the full list of deferred items with their decisions and the delivery metrics from the quality report. VALIDAR items still waiting (left by autonomous mode) go through the `validar` skill first; when it recorded a decision, run the gate again with `--report` and commit the updated report. Then ask whether to merge into the default branch and push. Do each only when the user says so, carrying it out with `superpowers:finishing-a-development-branch` for the option the user chose.
   **Test environment before production.** When the project has a test (staging) environment, the merged delivery is published there first, migrations included, and reaches production only after the user checks it there; backup and rollback are proven in that environment. You say what to publish and the user runs it or asks for it explicitly.
   **Where the time went.** Point out the largest time sink in the metrics and the most frequent finding origin, and propose one change for the next delivery (more parallelism, a spike, a check). When waiting for a shared resource (a single data store, login limits, a long interface test suite) is the largest time sink, propose the isolation lines of "Execução em paralelo" as the first task of the next delivery. After a resource pause, propose updating the per-copy peak in `CLAUDE.local.md` with what the pause notes show.
   **Plugin feedback:** offer the `feedback-plugin` skill.

## Autonomous mode
Only when the user turns it on (for example before leaving), recorded with `mode autonomous`:
- **Heartbeat.** Create a recurring job of this session with `CronCreate` (every 15 minutes, off the :00 and :30 marks) whose prompt is "pipeline heartbeat: run `ledger.py status` and continue the delivery", so a report that arrived without its completion notification never leaves the delivery idle. Create it only when `CronList` shows none. Delete it with `CronDelete` on `mode supervised` and when nothing more can move without the user (the gate READY on the last delivery the user queued, or the delivery stopped with `note --validar`); a resource pause (below) is not such a stop. On a resumed session in autonomous mode, check `CronList` and create it again if it is gone; it lives only in this session and expires after 7 days.
- **A resource runs out** (memory, disk, a port, a quota) and a step is killed or blocked: do not wait for the user. Stop the agents that are building or testing (`TaskStop`, then `release` their tasks) and the processes you started (by PID, never one you did not start), hold new dispatches, keep the heartbeat (while paused, it only checks the resource) and `note` the pause (the resource, how much was free, how many copies were up). Wait with a background command (Bash `run_in_background`) that checks the resource every few seconds and exits once it is back, so its completion wakes you without spending tokens while it waits; the heartbeat stays as the fallback if that command dies. Then resume (with fewer tasks in parallel when parallel work ran it out) and `note` the resumption.
- Approval 1 becomes the plan reviewer's PASS; the plan's product decisions and the design page are also `note --validar`.
- Never merge into the default branch, push or deploy; run git through the Bash tool, where the plugin's hook denies merging into and pushing the default branch while the ledger is in autonomous mode. Every `git push` asks the user, who is away, so the work branch is not pushed either. The next delivery starts on a branch stacked on this one (`git switch -c <branch>` from its head, then `start --slug <slug> --archive --base <this branch>` and `mode autonomous` again, since a new ledger starts supervised); its gate takes the base from the ledger.
- When the user is back: `mode supervised`, then run approval 2 (step 7, VALIDAR included) for each delivery, oldest first. For an earlier delivery, switch to its branch and pass `--ledger .superpowers/ledger-<its slug>.jsonl` to `gate.py` and to `ledger.py` (before its command), starting with `mode supervised`; a fix made there is merged into the stacked branch.

## Several sessions on one project
A delivery can be split across sessions (terminals): one front per session, split at a module boundary with no file in common, each in its own worktree (so its own ledger) and branch, with its sequential numbers reserved in the plan. One session integrates: it merges a front into the delivery branch (`git merge --no-ff`, so the gate does not count the front's reviewed commits as unreviewed) only after `ledger.py status --check` passes in that front's worktree, brings the front's notes, VALIDAR list and deferred decisions to approval 2, and runs the gate. Fronts in different repositories run in separate sessions with no coordination. To open a session yourself (a new terminal running `claude` in a folder): remove from its environment every `CLAUDE*` variable this session passes on (with `CLAUDE_CODE_CHILD_SESSION` the new session saves no transcript and never shows in `ListAgents`), give the terminal its command line as one string, and brief it with `SendMessage` only once `ListAgents` lists it; a tab that shows an error or never appears there did not start right: tell the user and have them close it before you open another, so two sessions never work the same front.

## Rules
- Pass agents file paths and ranges (plan, spec, `<from>..<head>`, ledger, the report files in `.superpowers/reports/`), not pasted content.
- Screen formats are those the project's `CLAUDE.md` lists. A delivery with screens and none listed: ask the user before the design round (or the first cycle) and write them on that line.
- Never fix code yourself; send it to the dev. The spec, the plan before approval, the plan's `## Errata`, `docs/lessons.md`, the quality report, the report files in `.superpowers/reports/` and the screen formats line of `CLAUDE.md` are the only files you edit.
- Before telling the user the code already does or has something, find it in the code and give its path.
- A flaky test (fails, then passes with no change) is never retried automatically, in the suite or by re-running until green: the `dev` finds the cause, or quarantines the test with the reason and you `defer` it.
- Keep `.superpowers/` out of commits.
- Never run a command an agent was denied (lint, a network call, killing a process) on its behalf: surface it to the user.
- Never merge into the default branch, push or deploy without the user's explicit request for that delivery.
- When you stop for the user (a product question, approval 1 or 2) or the gate is READY, also send one `PushNotification` line with what they need to do; the tool skips it while they are at the terminal. In autonomous mode, send it only when nothing more can move without the user (when you delete the heartbeat).
- Before installing any third-party skill, plugin, MCP server or hook, apply "Third-party extensions" in `${CLAUDE_PLUGIN_ROOT}/checklists/general.md` and tell the user the outcome.
