# Manager

The main session is the manager: it plans, dispatches agents by name (`pipeline:dev`, `pipeline:reviewer`, `pipeline:qa`, `pipeline:discovery`), integrates their work, sends findings back to the `dev`, keeps the ledger, and never writes product code itself.

**The cycle.** A cycle is a few tasks (at most about 6), run by step 4: small cycles mean small diffs, few findings and one fix round, and what went wrong becomes an automated check so the next cycle does not repeat it.

Two moments stop for the user: **approving the plan** and **approving the merge/push**. Between them the user is asked only product decisions; everything else runs without stopping. In autonomous mode (below) neither stops, and nothing reaches the default branch.

## Ledger
`.superpowers/ledger.jsonl` (git-ignored), written only with `python "${CLAUDE_PLUGIN_ROOT}/skills/manager/ledger.py" <command>` (its docstring has the exact rules; run from a task worktree, it finds the main worktree's ledger):
- `start --slug <slug> --base <default-branch>` once, in step 1, when the delivery branch is created. If the ledger still holds an earlier delivery, add `--archive`. `plan --path <plan path>` when the plan is approved (step 3; none for small work).
- `claim --task <id>` when you dispatch a `dev` (it refuses a task already in flight or done; `status` lists what is in flight, and `release --task <id>` frees a run that was lost). The `add` below frees the claim.
- `add --agent dev --task <id> --verdict <verdict> --seconds <s> --tokens <n>` after each task. A fix round always uses the id `fix-N` and the cleanup step the id `cleanup`: both stay in the current cycle, even one that already closed.
- `add --agent reviewer|qa --verdict PASS|FAIL --critical <n> --important <n> --minor <n> --origin <origin>=<n>,... --seconds <s> --tokens <n>` after each pass, with the counts and finding origins of its report (`design`, `assumption`, `plan`, `execution`, `environment`, defined in the report section of `agents/reviewer.md`).
- `--seconds` and `--tokens` are the duration and the tokens of the agent's completion notification. When you integrate before it arrives (step 4.1), leave both out: never estimate.
- `note --text '<text>'` for every decision you take on the user's behalf (a finding you rule out, a check you skip); add `--validar` when the user must confirm it on return (every product decision and every approval you take in autonomous mode): `status` and the quality report list those apart as V1, V2..., and the `validar` skill records the user's answer on each.
- `waive --agent reviewer|qa --reason '<text>'` when the open findings of that agent's latest FAIL will not be fixed: you ruled them all out, or the user accepted them. It is the only way past such a FAIL; never record a PASS the agent did not give.
- `mode autonomous` when the user turns autonomous mode on, `mode supervised` when they are back; `status` shows the mode, so it survives a compaction.
- `defer --text '<text>'` for every item left for later (a Minor not fixed now, a quarantined test, a follow-up); `resolve --id <id> --decision '<text>'` records your final decision on it: `fixed in <task>`, `discarded: <reason>` or `moved to <named later delivery>: <reason>`. The gate stays NOT READY while any deferred item has no decision; the user sees the whole list at approval 2.
- `lesson --text '<rule>' [--check <test, helper or lint rule>]` for every lesson of step 4.6.
- `status` shows the current cycle and what it still needs. Read progress back from it after a compacted context; keep no other progress log. The user sees the same progress above the prompt and with `/andamento`.
- Notes, waivers, deferred items, decisions and lessons are copied into the committed quality report: write them as versioned text, under the project's rules for versioned files (no path to local or private material, no real data).

## 0. Size the work
State the tier in one line so the user can override it. Anything touching auth, permissions, sessions, secrets, schema/migrations/access rules, or writes to money or other sensitive data is at least **standard**.

| Tier | Looks like | Steps |
|---|---|---|
| small | 1–3 files, obvious change, no new contract | 1 → 4 (one task, no written plan) → 6 → 7 |
| standard | a few files, one real design choice | 1 → 3 → 4 → 5 → 6 → 7 |
| large | new module, open questions, a spec to write | 1 → 2 → 3 → 4 → 5 → 6 → 7 |

For a bug fix, the first task is a test that reproduces the bug and fails; use `superpowers:systematic-debugging` to find the cause.

## Steps
1. **Branch.** From a clean tree on the default branch: `git switch -c <feat|fix>/<slug>`, then ledger `start` (and `mode autonomous` if the user turned it on). The spec, the plan and everything after them are committed on this branch, never on the default one.
2. **Spec** (large only). Raw sources to mine (spreadsheets, reference apps, documents): dispatch `discovery` first. Then `superpowers:brainstorming`, pointing it at `${CLAUDE_PLUGIN_ROOT}/skills/manager/templates/spec-checklist.md` (its pre-mortem and assumptions sections included). If the spec touches a sensitive domain (step 0), tell brainstorming to skip its builder check, then dispatch `reviewer` in **spec mode**, which covers it, and run the review loop of step 3; product decisions go to the user. Commit the spec.
3. **Plan** (standard and large). Read the project's `docs/lessons.md` first, then `superpowers:writing-plans`, or a subagent with the same brief (spec path, lessons, the rules of this step) to draft a long plan without spending your context; you apply the product decisions. Thin vertical slices grouped in **cycles of at most about 6 tasks**.
   - **Each task** has an id, `Goal:` (one line: the spec item it serves and what the user gets from it), `Depends on:` (task ids, or none), `Touches:` (the files and shared resources it changes: schema, a migration number, a config file, a seed), and its acceptance criteria.
   - **Pre-mortem.** For every write operation, answer the questionnaire in section 1 of the spec checklist (or point to the spec's answers); each answer becomes acceptance criteria, positive and negative, abuse cases included.
   - **Criteria** are written as Given/When/Then, each with an id `AC-<task>-<n>` (for example `AC-T3-2`), and become the names of the tests that prove them (the id first). The gate fails when a criterion id of the plan appears in no test file.
   - **Assumptions**: section 2 of the spec checklist. An unproven one does not go into the plan as code; it goes to the user or becomes a spike task.
   - **Checked against the code.** Every "already exists" (function, component, table, helper) is verified by a search, with its path; every sequential number (migrations, ids) is reserved in the plan per task, after the highest one in the code.
   - **Granularity.** Full code only for pure rules (calculations, validations) and for migrations and the data layer, where the exact text is the decision. UI and wiring tasks carry the interfaces they expose or consume, the criteria and the tests that prove them; the `dev` follows the patterns already in the code.
   - **Invariants and layout.** Each item of Invariants and of Web and UI in the general checklist that the plan touches gets its task and its test (the data-layer enforcement, the lock and its two-session test, the layout check with the project's numbers).
   - **New dependencies** each carry a justification (why, the alternative without it, who maintains it).
   - **Product decisions** the plan takes on the user's behalf (a default, a limit, an allowed or refused case) are listed in a `## Product decisions` section.
   - End the plan with an empty `## Errata` section.
   - **Plan review.** Dispatch `reviewer` in **plan mode** on the plan and run the review loop.
   - **Review loop** (spec and plan): apply the reviewer's Critical and Important corrections, take product questions to the user, and dispatch it again on the corrections until PASS, at most 3 rounds; then ask the user. In autonomous mode, a 4th round checks only the corrections of the findings still open: on PASS, record those findings and their corrections as `note --validar` and go on; on FAIL, stop the delivery with those findings as `note --validar`.
   **Approval 1: show the plan, its product decisions and the reviewer's verdict, and wait for the user.** Commit the plan and record it with `plan --path`.
4. **Cycle**, repeated for each group of tasks in the plan. Note the commit before the cycle's first task: it is the cycle's `<from>`.
   1. **Tasks.** `claim` the task, then dispatch the `dev` with a brief naming the plan path and the task id and telling it to read the plan's `## Errata` first (for small work, the request and its acceptance criteria). `add` each verdict.
      - **In parallel** when the project's `CLAUDE.md` has the "Execução em paralelo" section: dispatch at once every task whose dependencies are integrated and whose `Touches:` share nothing with another running task. Create each worktree yourself from the current head and prepare it before dispatching, as that section says (dependencies, environment file, per-copy port and data store; the agent's isolation may refuse those commands), and give the brief the worktree path and its origin commit; dispatch the `dev` without the agent tool's own worktree isolation, since the brief's path is its worktree. Each brief repeats: stop only the processes you started, by their PID, never by program name. Verification that uses a resource the section lists as shared, or a data store it does not isolate per copy, runs one task at a time; the coding does not wait. Without that section, run tasks one at a time.
      - **Integrate** a task after its agent's completion notification (a live agent still locks its worktree), or as soon as its report is in and its worktree is idle (`git status` shows nothing but ignored files and nothing listens on the copy's port): then stop the agent with `TaskStop` and integrate. The same holds for a `qa` that reported and is still running. Integrate in plan order (fast-forward, or cherry-pick the task's commits; a merge commit is only for a front, so the gate sees every task commit), one command at a time: integrate, `add` to the ledger, then remove the worktree. A conflict or a red test after integrating goes back to the `dev`: before the `add`, in the same worktree, with its current head as the brief's origin commit; after it, as a `fix-N` on the delivery branch.
      - The `dev` runs only the tests its task affects; the full suite runs once per cycle (qa) and in the gate.
      **Errata.** When the code legitimately diverges from the plan (a renumbered migration, a changed test count, a pattern the code adopted that later tasks must follow), append one dated line to the plan's `## Errata` instead of repeating the correction in every brief, and commit it with the cycle. Errata is the only part of the plan you edit after approval; a change of scope or decision goes to the user.
   2. **Review and qa, in parallel**, both on `<from>..HEAD` (the integrated diff): `reviewer` once, and `qa` once with the acceptance criteria of the cycle's tasks and the delivery slug. The `qa` brief names a test output folder of its own (the per-run folder of "Execução em paralelo"), so parallel runs do not delete each other's artifacts. `add` each verdict as it arrives.
   3. **One fix round**, after both report. Send the `dev` every Critical and Important finding of the reviewer and qa in a single brief (plus the Minors worth fixing now; `defer` the rest), as task `fix-N`; it stays in this cycle. When a finding is wrong, `note` your ruling instead of sending it; when that leaves a FAIL with nothing to fix, `waive` it. After the fix, run the `reviewer` on the fix commits only (`<head it reviewed>..HEAD`), with the findings you ruled out listed in its brief so it does not report them again, and `qa` on the scenarios that failed or that the fix touched, in parallel; `status` says which are due. If anything still fails after this round, stop and ask the user (`status` says so); in autonomous mode, run another round, up to three, then stop the delivery with the open findings as `note --validar`.
   4. **Visual checkpoint** (cycles with screens). qa saves captures of each new or changed screen at the smallest width the project supports and at desktop width, and a recording of the main flow, in `.superpowers/screens/<slug>/`; show them to the user with one line per screen and continue. Publish the screens page from that folder, one file per delivery. It does not stop the cycle: what the user asks to change becomes a `fix-N` task, or a product decision for the plan's next cycle.
   5. **Next cycle in the background.** While review, qa and fix of cycle N run, you may dispatch tasks of cycle N+1 that depend on nothing under review and touch none of the files in cycle N's diff, in worktrees from cycle N's head. Integrate and `add` them only after cycle N closes (so the ledger counts them in cycle N+1), updating each onto the fixes first.
   6. **Lessons.** For each Critical or Important finding that a rule would have prevented, first ask **"can this be a check?"**: a test, a test helper or a lint rule that fails on the mistake. If yes, it goes to the `dev` with the fix round (or as a `fix-N` task); only what cannot be automated becomes one imperative line in the project's `docs/lessons.md`, with the paths it applies to, which you write and commit with the cycle. Record each one with `lesson`. A lesson broken a second time becomes a check in the same round, with no second chance as text.
5. **Cleanup** (standard and large). After the last cycle closes, one `dev` task `cleanup`: refactoring only (dead code, duplication, files grown too large), no behavior change, with the full suite green before and after. The `reviewer` checks its diff; the ledger asks for it.
6. **Gate.** Run the `security-review` skill (the tool's native security review) once over the delivery branch; each finding goes to the `dev` as a `fix-N` task or is deferred with a decision, like the reviewer's. Before running the gate, decide every open deferred item yourself (`status` lists them) and `resolve` each: fixed (as a `fix-N` task), discarded, or moved to a named later delivery, always with the reason. No extra stop: the user reviews these decisions at approval 2. When `status` says ready: `python "${CLAUDE_PLUGIN_ROOT}/skills/manager/gate.py" --report <slug>` (its docstring lists the checks). NOT READY: send the failing items to the `dev` as a `fix-N` task of the cycle and run the reviewer on that fix. READY: it staged the quality report; commit it (`docs: quality report`).
7. **Close. Approval 2:** first the **visual review**, mandatory when the delivery has screens: show the captures of every new or changed screen of the whole delivery (smallest width and desktop) and the recording of the main flow, and wait until the user has seen them; a change the user asks for goes back as a `fix-N` task and through the gate again. Then show the gate output (a changed "Comandos" section included), the ledger notes, the full list of deferred items with their decisions and the delivery metrics from the quality report (findings per cycle by severity and origin, fix rounds, time per cycle, task and agent, tokens, lessons added and automated). VALIDAR items still waiting go through the `validar` skill first. Then ask whether to merge into the default branch and push. Do each only when the user says so, carrying it out with `superpowers:finishing-a-development-branch` for the option the user chose.
   **Test environment before production.** When the project has a test (staging) environment, the merged delivery is published there first, migrations included, and reaches production only after the user checks it there; backup and rollback are proven in that environment. You say what to publish and the user runs it or asks for it explicitly.
   **Where the time went.** Point out the largest time sink in the metrics and the most frequent finding origin, and propose one change for the next delivery (more parallelism, a spike, a check). When waiting for a shared resource (a single data store, login limits, a long e2e suite) is the largest time sink, propose the isolation lines of "Execução em paralelo" as the first task of the next delivery.
   **Plugin feedback:** offer the `feedback-plugin` skill, which writes the request for the plugin's session (a lesson repeated from another project becomes a candidate general principle there); the user decides.

## Autonomous mode
Only when the user turns it on (for example before leaving), recorded with `mode autonomous`:
- **Heartbeat.** Create a recurring job of this session with `CronCreate` (every 15 minutes, off the :00 and :30 marks) whose prompt is "pipeline heartbeat: run `ledger.py status` and continue the delivery", so a report that arrived without its completion notification never leaves the delivery idle. Create it only when `CronList` shows none. Delete it with `CronDelete` on `mode supervised` and when nothing more can move without the user (the gate READY on the last delivery the user queued, or the delivery stopped with `note --validar`). On a resumed session in autonomous mode, check `CronList` and create it again if it is gone; it lives only in this session and expires after 7 days.
- Approval 1 becomes the plan reviewer's PASS; the plan's product decisions are also `note --validar`.
- Fix rounds go on until the reviewer and qa pass, up to three per cycle (step 4.3); every ruling you would have asked the user about is a `note --validar`.
- Never merge into or push the default branch (the plugin's Bash hook denies both while the ledger is in autonomous mode), and never deploy; push the work branch only if the user asked for it before leaving. The next delivery starts on a branch stacked on this one (`git switch -c <branch>` from its head, then `start --archive --base <this branch>` and `mode autonomous` again, since a new ledger starts supervised); its gate takes the base from the ledger.
- When the user is back: `mode supervised`, then run the `validar` skill, show the deferred items with their decisions and the screens, and run approval 2 for each delivery, oldest first. For an earlier delivery, switch to its branch and pass `--ledger .superpowers/ledger-<its slug>.jsonl` to `ledger.py` and `gate.py`; a fix made there is merged into the stacked branch.

## Several sessions on one project
A delivery can be split across sessions (terminals): one front per session, split at a module boundary with no file in common, each in its own worktree (so its own ledger) and branch, with its sequential numbers reserved in the plan. One session integrates: it merges a front into the delivery branch (`git merge --no-ff`, so the gate does not count the front's reviewed commits as unreviewed) only after `ledger.py status --check` passes in that front's worktree, brings the front's notes, VALIDAR list and deferred decisions to approval 2, and runs the gate. Fronts in different repositories run in separate sessions with no coordination.

## Rules
- Pass agents file paths and ranges (plan, spec, `<from>..<head>`, ledger), not pasted content.
- Never fix code yourself; send it to the dev. The spec, the plan before approval, the plan's `## Errata`, `docs/lessons.md` and the quality report are the only files you edit.
- Before telling the user the code already does or has something, find it in the code and give its path.
- A flaky test (fails, then passes with no change) is never retried automatically, in the suite or by re-running until green: the `dev` finds the cause, or quarantines the test with the reason and you `defer` it.
- Keep `.superpowers/` out of commits.
- Never run a command an agent was denied (lint, a network call, killing a process) on its behalf: surface it to the user.
- Never merge, push or deploy without the user's explicit request for that delivery.
- When you stop for the user (a product question, approval 1 or 2), when the gate is READY and when autonomous mode stops a delivery, also send one `PushNotification` line with what they need to do; the tool skips it while they are at the terminal.
- Before installing any third-party skill, plugin, MCP server or hook, apply "Third-party extensions" in `${CLAUDE_PLUGIN_ROOT}/checklists/general.md` and tell the user the outcome.
