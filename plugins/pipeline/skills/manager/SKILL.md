# Manager

Runs one delivery (module, feature, or bug fix) through the `pipeline` plugin's agents. **The main session is the manager:** only the main session can dispatch agents, so orchestration lives here and not in an agent. It plans, dispatches agents by name (`subagent_type`, always with the plugin prefix: `pipeline:dev`, `pipeline:db`, `pipeline:gate`, and so on), routes findings, keeps the ledger, and never writes product code itself. Agents do not run on their own; name them. The final release check is the `gate` agent, which reads the ledger and never dispatches anyone.

## Ledger (how agents stay in sync)
One file per delivery, `.superpowers/ledger.jsonl` in the worktree root (git-ignored), written only through `python "${CLAUDE_PLUGIN_ROOT}/skills/manager/ledger.py" --ledger .superpowers/ledger.jsonl <command>`:
- `start --slug <slug> --base <sha>` once, before the first dispatch (the spec review's, when step 2 runs).
- `append --task <id> --from <sha> --head <sha> --report <path> --line '<agent LEDGER line>'` after every agent returns. `--from` is the parent of the task's first commit (the branch base for a small change) and `--head` is the current HEAD, so the entry records the exact commit range the agent covered. Round numbers are computed per task and agent.
- The task id `spec` is reserved for the spec review (step 2): its lines also take `--spec <path>`, the reviewed document, which must exist in `--head`. Only the reviewers `security`, `db`, `audit`, `design` and `code-review` can appear on it. Its findings are counted apart from the delivery's (`spec_totals`, not `totals`), so defects caught before any code do not lower the quality scores.
- `note --kind ruling|deferred|parked|condition --task <id> --text '<text>'` for every decision you take on the user's behalf (a finding you rule on, a Minor you defer or park, a condition attached to an approval, a spec review skipped). Notes are how decisions survive a compacted context.
- `status [--json] [--head HEAD]` shows the latest verdict per task and agent, the findings raised so far, and the notes; with `--head`, each entry whose range ends before that commit is marked `STALE` with the number of commits after it. A `spec` entry is marked `STALE` only when its spec file changed after the review, not when code commits follow it.

This ledger is the only progress record of the delivery: do not also keep a `progress.md` or any second log, and read progress back from `status` after a context compaction.

Package files for agents come from `python "${CLAUDE_PLUGIN_ROOT}/skills/manager/package.py"`, so nothing is pasted into a prompt: `brief --plan <plan> --task <n> --out <file>` extracts one task's text, and `review --base <sha> --head <sha> --name <task>-r<round>` writes `.superpowers/reviews/review-<name>.diff` (commits, stats, diff) and a commit-by-commit `.history.patch` (needed to catch a secret that was added and later removed).

Every agent ends its report with one line `LEDGER {...}`; append it verbatim. `append` validates before writing: a known agent and a verdict valid for it (`PASS`/`FAIL` for reviewers, `DONE`/`DONE_WITH_CONCERNS`/`NEEDS_CONTEXT`/`BLOCKED`/`NO_DOC_CHANGE_NEEDED` otherwise), integer `new`/`open` counts for all three severities on a reviewer line, a verdict consistent with them (FAIL exactly when a critical or important finding is open), `--from`/`--head` that are commits in ancestor order, and an existing `--report` file. On a rejection nothing is written: re-read the saved report, fix the transcription or ask the agent for a corrected line, and append again. Save each agent's full report to `.superpowers/reports/<task>-<agent>-r<round>.md` first (`spec-<agent>-r<round>.md` for the spec review) (reviewers are read-only and cannot save it), and pass that path as `--report`; the `gate` cross-checks ledger lines against these files.

Give every agent the ledger path in its brief. Agents read it (never write it) to see what already ran and which findings are open, so parallel reviewers do not repeat each other and a fixer sees what is still pending.

## Where this applies
Only in repos where the `pipeline` plugin is enabled: enabling it is what loads this skill, the agents and the secret-scan hook, so it is the only switch. If the project lacks the structure (`CLAUDE.md`, `docs/`), run `pipeline:kickoff` first.

## Steps

1. **Scope and pre-flight, with evidence.** Identify the target and locate its spec and its living doc (`docs/NN-*.md`). Check:
   - `CLAUDE.md` and the `docs/` convention exist. If not, stop and offer `kickoff`.
   - A spec exists for the target. If not, stop and start `discovery` (raw sources) then `superpowers:brainstorming`. If it exists, skip both. Either way the spec goes through step 2 before any plan; brainstorming ends by handing off to `writing-plans`, so intercept that hand-off and run step 2 first. Skip step 2 only when `ledger.py status` already shows a passing `spec` review of the current spec or a `spec` ruling note.
   - Git repo with at least one commit and a clean tree (worktrees and the `gate` diff need a baseline). If not, ask the user how to proceed.
   - Prerequisites the target depends on (project scaffold, migrations, auth) exist. If not, the plan starts with a foundation task.
   - The `Comandos` section of `CLAUDE.md` lists how to run, test, typecheck, and lint (`qa` needs them). If it holds placeholders, derive the commands from the project (`package.json`, `Makefile`) and fill it in before planning.
   - `docs/quality-reports/` exists. Its presence turns on the push gate (the plugin's hook blocks a `git push` unless the `gate` approved the tree of every ref it sends). If missing, the first commit on the worktree branch adds `docs/quality-reports/.gitkeep`.
2. **Spec review, before the plan.** The reviewers read the approved spec, not code, so a design defect (a policy scoped to the wrong column, an invite that can cross tenants, a sensitive write with no trail) is fixed while it costs one edit instead of a migration and a rewrite.
   1. **Decide if it is required.** Required when the spec touches auth, permissions, sessions, RLS/access policies, schema or migrations, secrets, or writes to sensitive or financial data. Otherwise optional: ask the user. When it does not run, record why with `note --kind ruling --task spec` (the `gate` looks for this note when the branch touches those domains); a bug fix with no design change of its own records that as the reason.
   2. **Prepare.** Commit the spec (and any related doc it changed) so a commit holds the reviewed text. If the ledger does not exist yet, `start` it now in this checkout, with `--base` = `git merge-base HEAD <default-branch>`. Note `--from` = the parent of the spec's first commit.
   3. **Choose reviewers by the spec's domain**: `security` for auth, permissions, sessions, secrets, RLS; `db` (reviewer mode) for schema, migrations, RLS, queries; `audit` for writes to sensitive or financial data; `design` when the spec describes UI; `code-review` when it defines contracts or interfaces complex enough to get wrong (optional otherwise). Dispatch them in one message so they run in parallel, each in **spec mode**: the brief gives the spec path, the related files it builds on (schema, other specs, the project's `CLAUDE.md`), the ledger path, and states that there is no diff.
   4. **Record.** Save each report to `.superpowers/reports/spec-<agent>-r<round>.md` and append it with `--task spec --spec <spec path> --from <sha> --head <HEAD>`.
   5. **Fix loop.** For Critical and Important findings, apply the corrections in the spec in this session (the spec is a design document, not product code, and the brainstorming that wrote it lives here); take to the user every correction that is a product decision (scope, behavior the user would notice, a trade-off between options) and apply their answer. Commit, then re-run the same reviewers over the updated spec (`--from` unchanged, new `--head`) until each one PASSes. Maximum 5 rounds per reviewer; at round 5 still FAIL, stop and ask the user. Minors: apply them, or record each with `note --kind deferred --task spec`.
   Only then move to the plan, which inherits the corrected spec. A later edit to the spec marks its reviews `STALE` in `status --head HEAD`; re-run them on the current text before the gate.
3. **Plan.** Use `superpowers:writing-plans`. Tag each task with an id, its implementer (`dev` for app code, `db` for schema, migrations, RLS) and its required reviewers. Show the plan and wait for approval.
4. **Execute** in a worktree (`superpowers:using-git-worktrees`) with the loop below. Do not invoke `superpowers:subagent-driven-development`: it keeps its own progress ledger and reviewer prompts, which would compete with this ledger and these agents. If step 2 created the ledger, copy `.superpowers/ledger.jsonl` and `.superpowers/reports/` into the worktree root before the first dispatch (`.superpowers/` is git-ignored, so the worktree starts without them); otherwise run ledger `start` first. One implementer at a time. Per task, in order:
   1. Implementer (`dev` or `db`), who commits the task on the worktree branch. Commits stay local; never on the default branch. Give it the task's `brief` file. Note the task's `--from` (HEAD before it) and append its report to the ledger.
   2. `docs` updates the matching `docs/NN-*.md` (or reports `NO_DOC_CHANGE_NEEDED`). Append to the ledger.
   3. Reviewers for the diff, in one message so they run in parallel: `code-review` always; `db` and `security` for schema, migrations, RLS; `security` for auth, permissions, secrets; `audit` for writes to sensitive or financial data; `design` for UI. Capture HEAD before dispatching, build one `review` package for the range and use that HEAD as `--head` for all of them. Append each report to the ledger. The `db` review is a fresh `db` run in reviewer mode; the ledger keeps its rounds and latest entry apart from the `db` implementer's.
   4. `qa`, in a second dispatch, once every reviewer of step 3 reports PASS: it validates the same range (same `review` package and `--head`), so it runs against code that is not about to change. Append its report to the ledger.
   5. Findings go to the agent that owns the file. After the fix commit, re-run the same reviewer over the task's full range (`--from` unchanged, new `--head`) so its latest entry covers the fix. Maximum 5 rounds per task and reviewer (the ledger's `round`); at round 5 still FAIL, stop and ask the user.
   For a bug fix, run `superpowers:systematic-debugging` first and require a regression test.
   Never leave a commit uncovered: any commit made after a reviewer's `--head` in that reviewer's domain means that reviewer runs again.
5. **Gate.** Run ledger `status --head HEAD` and fix every entry it marks `STALE` (commits after that reviewer's range, or a spec edited after its review) or missing before calling the gate; a wasted gate run is a full-branch review. Then dispatch `gate` with the branch base, the ledger path and the reports directory; it reviews the whole branch (`<base>...HEAD`) and its commit history. On APPROVED it writes and stages the quality report and records the approval. On BLOCKED, each item names its owner: route it to step 4 (implementer, or the missing/stale reviewer) or step 2 (a missing or stale spec review), append the new reports to the ledger and call the gate again.
6. **Leave the machine.** After APPROVED, commit the staged report as is, with nothing else added. Merge into the default branch and push only when the user asks, each time; nothing merges or pushes without their request. Finish with `superpowers:finishing-a-development-branch`.
7. **Close.** End with two lists taken from `ledger.py status`: "Rulings I made" (every `ruling` note, in order, with what it costs if wrong) and the `deferred`/`parked`/`condition` notes still standing. Then list every deviation from this procedure: agent not dispatched, improvisation, anything that blocked.

## Small-change lane
Decide from the actual diff, never from how small the request sounds. The lane applies only if the change touches at most 3 files and 100 lines and none of: migrations, schema, RLS, auth, permissions, sessions, env/secrets config, write paths for sensitive or financial data. Then skip the written plan and run: `dev` (commits on a worktree branch), `code-review`, `docs` only if an interface or setup step changed, `qa` (always: the `gate` requires it; with no tests for the area, `qa` verifies by hand and says so, which the `gate` scores as a coverage gap), then `gate` as in steps 5 and 6. The ledger applies unchanged (a single task, `--from` = base). There is no spec review: the lane excludes every domain that makes it required. If the diff exceeds any limit, switch to the full procedure.

## Rules
- Keep `.superpowers/` out of commits.
- Pass agents file paths (briefs, diffs, reports, ledger), not pasted content.
- Never fix findings yourself in the manager session; route them. The one exception is the spec in step 2, which this session wrote and corrects.
- Never edit the ledger by hand; only through `ledger.py`.
- Keep one progress record: the ledger. No `progress.md`, no second log.
