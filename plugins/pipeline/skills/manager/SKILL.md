# Manager

Runs one delivery (module, feature, or bug fix) through the `pipeline` plugin's agents. **The main session is the manager:** only the main session can dispatch agents, so orchestration lives here and not in an agent. It plans, dispatches agents by name (`subagent_type`, always with the plugin prefix: `pipeline:dev`, `pipeline:db`, `pipeline:gate`, and so on), routes findings, keeps the ledger, and never writes product code itself. Agents do not run on their own; name them. The final release check is the `gate` agent, which reads the ledger and never dispatches anyone.

## Ledger (how agents stay in sync)
One file per delivery, `.superpowers/ledger.jsonl` in the worktree root (git-ignored), written only through `python "${CLAUDE_PLUGIN_ROOT}/skills/manager/ledger.py" --ledger .superpowers/ledger.jsonl <command>` (always this literal path, never a command stored in a shell variable):
- `start --slug <slug> --base <sha>` once, before the first dispatch (the spec review's, when step 2 runs). It records the per-task report layout; `--layout per-file` keeps the 1.4.0 one-file-per-report layout.
- `save-report --task <id> --agent <agent> --from <sha> --head HEAD --round auto --stdin` (or `--file <f>`) appends an agent's full report verbatim, as one section, to `.superpowers/reports/<task>.md` and prints `<path>#<anchor>` (anchor `<agent>-r<N>`, `db-review-r<N>` for a `db` review); the section heading names the agent, round and range. The file is append-only: `<task>.md.sums` holds a hash of the file up to the end of each section, and `save-report` refuses to append to a file changed by hand. Parallel reviewers can save to the same task at once: each save holds `<task>.md.lock` (waits up to about 10 s, takes over a lock whose process died or that is older than 30 s, by moving that exact lock file aside so two waiting saves cannot both take it; a save only ever removes its own lock). `auto` counts the ledger rounds of that task, agent and role, the way `append` numbers them. For `db` pass `--role implementer` or `--role reviewer` (on the `spec` task it is always reviewer). The other agents have one role, inferred. Feed it the report exactly as returned (stdin, or a scratch file written with the Write tool); never summarize or retype it. You are the one transcribing the agent's final message, so copy it whole and verbatim: every section, the findings with their file:line, the verdict and the `LEDGER` line, with no reformatting, no dropped "Checked"/"Notes" parts and no fixes to its wording. If the message reached you truncated or garbled, ask the agent to resend it (SendMessage) rather than reconstructing it. A save interrupted between writing the section and recording it leaves unrecorded bytes at the end of the file: `save-report` and `verify-reports` then refuse it and point at `repair-reports --task <id>`, which shows those bytes (and whether they are the interrupted section) and truncates them only with `--yes`; save the report again afterwards. A ledger started before 1.5.0 keeps the per-file layout (`<task>-<agent>[-review]-r<N>.md`, no `--from` needed).
- `append --task <id> --from <sha> --head HEAD --report <path#anchor> --line '<agent LEDGER line>' [--scope fix|full]` after every agent returns. `--from` is the parent of the task's first commit (the branch base for a small change); `--head HEAD` (any rev) is resolved to the current SHA, so the entry records the exact commit range the agent covered. Round numbers are computed per task and agent. `--scope fix` (reviewers only) records a fix-only re-review: `--from` must be that agent's previous head on the task, and the entry keeps `covers_from`, the start of the chain, so a full review followed by contiguous fix reviews covers the whole task range. `append` refuses `--scope fix` for `security` and `db`, and when the fix range touches a file outside the open findings of the task's reviewers (the same check `review --fix-of` makes): use the `--scope` the package printed. Without it the scope is `full`. The entry records `report_sha256`, the hash of the report section's bytes.
- `verify-reports [--json]` checks every report the ledger cites: per-task files only grew (every recorded prefix hash matches, no unrecorded bytes), every anchor exists, per-file reports exist, and each report's bytes still match the entry's `report_sha256`. It detects tampering, it does not prevent it (a report, its `.sums` and the ledger line can be rewritten together), so the `gate` still reads the reports. `show-report <path#anchor>` prints one section.
- The task id `spec` is reserved for the spec review (step 2): its lines also take `--spec <path>`, the reviewed document, which must exist in `--head`. Only the reviewers `security`, `db`, `audit`, `design` and `code-review` can appear on it. Its findings are counted apart from the delivery's (`spec_totals`, not `totals`), so defects caught before any code do not lower the quality scores.
- `note --kind ruling|deferred|parked|condition --task <id> --text '<text>'` for every decision you take on the user's behalf (a finding you rule on, a Minor you defer or park, a condition attached to an approval, a spec review skipped, a spec detail corrected during execution). Notes are how decisions survive a compacted context.
- `status [--json] [--head HEAD]` shows the latest verdict per task and agent (with the range its fix chain covers), the findings raised so far, and the notes; with `--head`, a reviewer entry is marked `STALE` when a later commit modifies a file of its reviewed range, or when a later commit is reviewed by no other task; each such commit is listed under it with the files it touched. A later commit of another task that touches none of its files and is inside that task's reviewed range leaves it current. A `spec` entry is marked `STALE` only when its spec file changed after the review. An entry whose fix-scoped chain is broken (a `--scope fix` line with no earlier entry ending at its `--from`) shows `chain broken` in place of its range and is `STALE` with or without later commits.
- `lesson add|mark|list|promote|sync` manages the delivery's lessons (see "Lessons").

This ledger is the only progress record of the delivery: do not also keep a `progress.md` or any second log, and read progress back from `status` after a context compaction.

`append` validates before writing: a known agent and a verdict valid for it (`PASS`/`FAIL` for reviewers, `DONE`/`DONE_WITH_CONCERNS`/`NEEDS_CONTEXT`/`BLOCKED`/`NO_DOC_CHANGE_NEEDED` otherwise), integer `new`/`open` counts for all three severities on a reviewer line, a verdict consistent with them (FAIL exactly when a critical or important finding is open), `--from`/`--head` that are commits in ancestor order, and an existing `--report` file (for `path#anchor`, a saved section of an intact per-task file whose anchor names this line's agent, `db-review-r<N>` for a `db` review, and whose heading names the same `--from..--head`). For `dev`, `db` and `docs` it also rejects a placeholder report (no `LEDGER` line; a `DONE`/`DONE_WITH_CONCERNS` report under 200 non-space characters, or a `NO_DOC_CHANGE_NEEDED`/`BLOCKED`/`NEEDS_CONTEXT` reason under 40; only "placeholder"/"TODO"), a `dev`/`db` report without a commit SHA inside the range or whose `Commit:` line is a placeholder (`<sha>`, "see git rev-parse", `HEAD` with no hex SHA; the agent pastes the real short SHA from `git rev-parse --short HEAD`), and a report whose "Files:" list names tracked files missing from `git diff --name-only FROM..HEAD`. On a rejection nothing is written: send the agent back for a corrected report (never fix its claims yourself), save it, and append again. To accept such a report anyway, pass `--allow-unlisted '<reason>'`: the reason is required and `append` records the ruling note itself. The `gate` cross-checks ledger lines against the saved reports.

Package files for agents come from `python "${CLAUDE_PLUGIN_ROOT}/skills/manager/package.py"`, so nothing is pasted into a prompt:
- `brief --plan <plan> --task <id> --out <file>` extracts one task (ids like `T1.2`, `3`, `A-1`), appends every `.superpowers/briefs/<task>.addenda/*.md` and `.superpowers/briefs/all.addenda/*.md`, then a `## Lessons` section chosen by the task's file paths (`--no-lessons` to skip). **Never edit a generated brief**: put extra instructions in an addenda file and regenerate, so re-extracting never loses them.
- `review --base <sha> --head <sha> --name <task>-r<round>` writes `.superpowers/reviews/review-<name>.diff` (commits, stats, diff; lockfiles only in the stat unless `--include-lockfiles`) with a `## Checklists` header listing the stack checklists that match the changed files, and a commit-by-commit `.history.patch` (needed to catch a secret that was added and later removed).
- `review --fix-of <task> --agent <agent> --head HEAD` builds a re-review package after a fix. From the ledger it takes that agent's last review of the task (its head and report) and decides the scope: `fix-only` (range = previous head..HEAD) when every file the fix touches, outside `docs/**` (always exempt), is cited in the open findings of the task's reviewers: the union of the findings of each reviewer's latest report on the task up to this agent's previous head, its own included, because one fix brief usually answers several reviewers at once (the findings are the sections under a severity heading or label, `## Important`, `**Minor**`, `Findings:`, up to the next other heading or label such as `Notes:`, `Open questions:`, `Checked:` or `## Other domains`; a cited path matches a changed file when equal to it or a `/`-bounded suffix of it, and a bare name or shorthand such as `04_privilegios.sql` or `0002:226` matches when it names exactly one file of the task by the start of its basename; ratios such as `4.5:1`, `e.g.`/`i.e.`, URLs and tokens without a letter are prose, not paths); `full (<reason>)` (range = the task's covered start..HEAD) when the fix touches another file, no open finding cites a file, a report cannot be read, or the agent is `security` or `db`, which always re-review the full range. A fix-only reviewer still reads the whole fix diff, including the parts that answer other reviewers. The package starts with `Scope:`, `Previous report:` and the `append` flags to record it with (`--from`, `--scope fix|full`). On the `spec` task the diff is limited to the spec file.

Every agent ends its report with one line `LEDGER {...}`; append it verbatim. Give every agent the ledger path in its brief. Agents read it (never write it) to see what already ran and which findings are open, so parallel reviewers do not repeat each other and a fixer sees what is still pending.

## Lessons
A lesson is one atomic, imperative rule (≤ 280 chars) that would have prevented a reviewer finding. Global lessons live in the plugin (`${CLAUDE_PLUGIN_ROOT}/lessons/<stack>.jsonl`, stacks `postgres-supabase`, `nextjs-react`, `auth`, `general`); the delivery's live in `.superpowers/lessons.jsonl`, written only by `ledger.py lesson`. `brief` injects the matching ones into every implementer brief.
- **Add** when you route a Critical or Important finding that a stated rule would have prevented: `lesson add --id <kebab-id> --stack <stack> --paths "<glob>,<glob>" --text '<rule>' --task <id> --agent <reviewer> --finding '<one line>'`. Paths are the globs of the files the rule applies to (empty only for a `general` rule that fits every task).
- **Mark** in later tasks whose brief carried the lesson, delivery or global alike: `lesson mark --id <id> --held` when the reviewers found nothing of that class, `--recurred` when one did (reviewers tag such findings `lesson:<id>`). For a global lesson, `mark` (and every brief that injects it) counts in a counters-only override row of the delivery file (`"override": true`); the global file is untouched and `brief` ranks by global plus override counters. Regenerating a brief that already exists does not count it again. A lesson that recurs twice needs enforcement (a test, a checklist item, a template), not more text: say so at step 7.
- **Promote** and **sync** only at step 7, after the user approves (see step 7). Never promote or sync on your own.

## Where this applies
Only in repos where the `pipeline` plugin is enabled: enabling it is what loads this skill, the agents and the secret-scan hook, so it is the only switch. If the project lacks the structure (`CLAUDE.md`, `docs/`), run `pipeline:kickoff` first.

## Steps

1. **Scope and pre-flight, with evidence.** Identify the target and locate its spec and its living doc (`docs/NN-*.md`). Check:
   - `CLAUDE.md` and the `docs/` convention exist. If not, stop and offer `kickoff`.
   - A spec exists for the target. If not, stop and start `discovery` (raw sources) then `superpowers:brainstorming`, pointing it at `${CLAUDE_PLUGIN_ROOT}/skills/manager/templates/spec-checklist.md`: the spec must answer every section of it. If it exists, skip both. Either way the spec goes through step 2 before any plan; brainstorming ends by handing off to `writing-plans`, so intercept that hand-off and run step 2 first. Skip step 2 only when `ledger.py status` already shows a passing `spec` review of the current spec or a `spec` ruling note.
   - Git repo with at least one commit and a clean tree (worktrees and the `gate` diff need a baseline). If not, ask the user how to proceed.
   - Prerequisites the target depends on (project scaffold, migrations, auth) exist. If not, the plan starts with a foundation task.
   - The `Comandos` section of `CLAUDE.md` lists how to run, test, typecheck, and lint (`qa` needs them). If it holds placeholders, derive the commands from the project (`package.json`, `Makefile`) and fill it in before planning.
   - `docs/quality-reports/` exists. Its presence turns on the push gate (the plugin's hook blocks a `git push` unless the `gate` approved the tree of every ref it sends). If missing, the first commit on the worktree branch adds `docs/quality-reports/.gitkeep`.
2. **Spec review, before the plan.** The reviewers read the approved spec, not code, so a design defect (a policy scoped to the wrong column, an invite that can cross tenants, a sensitive write with no trail) is fixed while it costs one edit instead of a migration and a rewrite.
   1. **Decide if it is required.** Required when the spec touches auth, permissions, sessions, RLS/access policies, schema or migrations, secrets, or writes to sensitive or financial data. Otherwise optional: ask the user. When it does not run, record why with `note --kind ruling --task spec` (the `gate` looks for this note when the branch touches those domains); a bug fix with no design change of its own records that as the reason.
   2. **Prepare.** Commit the spec (and any related doc it changed) so a commit holds the reviewed text. If the ledger does not exist yet, `start` it now in this checkout, with `--base` = `git merge-base HEAD <default-branch>`. Note `--from` = the parent of the spec's first commit.
   3. **Choose reviewers by the spec's domain**: `security` for auth, permissions, sessions, secrets, RLS; `db` (reviewer mode) for schema, migrations, RLS, queries; `audit` for writes to sensitive or financial data; `design` when the spec describes UI; `code-review` when it defines contracts or interfaces complex enough to get wrong (optional otherwise). Dispatch them in one message so they run in parallel, each in **spec mode**: the brief gives the spec path, the related files it builds on (schema, other specs, the project's `CLAUDE.md`), `templates/spec-checklist.md`, the stack checklists (`${CLAUDE_PLUGIN_ROOT}/checklists/*.md`) that fit the spec's domain, the ledger path, and states that there is no diff.
   4. **Record.** `save-report --task spec --from <sha>` each report and append it with `--task spec --spec <spec path> --from <sha> --head HEAD`.
   5. **Fix loop.** For Critical and Important findings, apply the corrections in the spec in this session (the spec is a design document, not product code, and the brainstorming that wrote it lives here); take to the user every correction that is a product decision (scope, behavior the user would notice, a trade-off between options) and apply their answer. Commit, then re-run the same reviewers with a `review --fix-of spec --agent <agent>` package each (the spec diff since their last review and their previous report; `security` and `db` re-read the whole spec) and record each with the `--from`/`--scope` its package prints, until each one PASSes. Maximum 5 rounds per reviewer; at round 5 still FAIL, stop and ask the user. Minors: apply them in a round that runs anyway; Minors from the **final** round go to the plan instead (`note --kind deferred --task spec` for each, and the plan task that absorbs it), so the spec is not re-reviewed for them.
   Only then move to the plan, which inherits the corrected spec. If a plan already existed, revise it against the diff of the spec since the plan was written.
3. **Plan.** Use `superpowers:writing-plans`. Tag each task with an id, its implementer (`dev` for app code, `db` for schema, migrations, RLS), its required reviewers, and a "Files:" list (lessons and checklists are chosen from those paths). Check current versions (`npm view`, docs) before fixing scaffold commands in the plan. Show the plan and wait for approval.
4. **Execute** in a worktree created **from the module branch** (where the spec and plan are), not from the default branch: run `git worktree add .claude/worktrees/<name> -b <branch> <module-branch>`, then `EnterWorktree` with that path. Copy the seed into the worktree root: `.superpowers/ledger.jsonl`, `reports/`, `briefs/` and `lessons.jsonl` when they exist (`.superpowers/` is git-ignored, so the worktree starts without them); with no ledger yet, run ledger `start` first. Do not invoke `superpowers:subagent-driven-development`: it keeps its own progress ledger and reviewer prompts, which would compete with this ledger and these agents. Run git as plain, separate commands (no `&&` chains, no heredocs mixing git with other tools): the worktree guard refuses compound commands. Edit `.superpowers/` files with Edit/Write. One implementer at a time. Per task, in order:
   1. Implementer (`dev` or `db`), who commits the task on the worktree branch. Commits stay local; never on the default branch. Give it the task's `brief` file. Note the task's `--from` (HEAD before it), then `save-report` (`--role implementer` for `db`) and `append` its report.
   2. `docs` updates the matching `docs/NN-*.md` (or reports `NO_DOC_CHANGE_NEEDED`). Save and append.
   3. Reviewers for the diff, in one message so they run in parallel: `code-review` always (with independent mutation testing when the task touches migrations, SQL functions or pure rule modules); `db` and `security` for schema, migrations, RLS; `security` for auth, permissions, secrets (including any change to `.pipeline-secrets-allow`); `audit` for writes to sensitive or financial data; `design` for UI. Capture HEAD before dispatching, build one `review` package for the range and use that HEAD as `--head` for all of them. Each reviewer opens the checklists listed in the package that name its role. Save and append each report. The `db` review is a fresh `db` run in reviewer mode, saved with `--role reviewer`; the ledger keeps its rounds and latest entry apart from the `db` implementer's.
   4. `qa`, in a second dispatch, once every reviewer of step 3 reports PASS: it validates the same range (same `review` package and `--head`), so it runs against code that is not about to change. Save and append.
   5. Findings go to the agent that owns the file, through a fix addenda file (`.superpowers/briefs/<task>.addenda/fix-r<round>.md`) listing this round's findings and asking the implementer to check how the fixes interact (same route, state or screen) and to test each fix's path and their combination. Add a lesson for each preventable finding (see "Lessons"). After the fix commit, re-run the same reviewer with its own `review --fix-of <task> --agent <agent>` package: fix-only (the fix diff plus its previous report) when the fix stays inside the files cited by the open findings of the task's reviewers (a fix brief addressing several reviewers stays eligible; `docs/**` never counts against it), the task's full range otherwise and always for `security` and `db`. Record it with the `--from` and `--scope` the package prints, so the ledger chain still covers the whole task. The `gate` reviews the whole branch regardless. Maximum 5 rounds per task and reviewer (the ledger's `round`); at round 5 still FAIL, stop and ask the user.
   For a bug fix, run `superpowers:systematic-debugging` first and require a regression test that failed before the fix.
   Never leave a commit uncovered: a commit made after a reviewer's `--head` that touches a file of that reviewer's task range, or that no reviewer of its own task covers, means that reviewer runs again (`status --head HEAD` lists both).
   - **Verify before recording** when the harness warns that the safety classifier was unavailable for an agent: read `git show --stat` and the diff of its commits yourself before `append`.
   - **Denied commands**: never run a command an agent was denied (lint, killing a process, a network call) on its behalf; that would bypass the permission. Surface it to the user and let them decide.
   - **Spec edits during execution.** A detail correction (a message text, an error code name, a value that changes no decision) is made with the code, documented by `docs`, recorded with `note --kind ruling --task spec`, and checked by that task's reviewers. A decision change (behavior, scope, data model, a security or audit property) goes to the user first and reopens the spec review for the affected domains. Before the gate, re-run every `STALE` spec reviewer once, in one batch, on the current spec, giving them the detail notes.
5. **Gate.** Run ledger `status --head HEAD` and `verify-reports`, and fix every entry marked `STALE` (a later commit touching its files or reviewed by no other task, a broken fix chain, or a spec edited after its review), every report problem, and every missing review before calling the gate; a wasted gate run is a full-branch review. Then dispatch `gate` with the branch base, the ledger path and the reports directory; it reviews the whole branch (`<base>...HEAD`) and its commit history. On APPROVED it writes and stages the quality report and records the approval. On BLOCKED, each item names its owner: route it to step 4 (implementer, or the missing/stale reviewer) or step 2 (a missing or stale spec review), append the new reports to the ledger and call the gate again.
6. **Leave the machine.** After APPROVED, commit the staged report as is, with nothing else added. Merge into the default branch and push only when the user asks, each time; nothing merges or pushes without their request. Finish with `superpowers:finishing-a-development-branch`.
7. **Close.** End with two lists taken from `ledger.py status`: "Rulings I made" (every `ruling` note, in order, with what it costs if wrong) and the `deferred`/`parked`/`condition` notes still standing. Then present each delivery lesson from `lesson list` (text, stack, paths, counters, source finding) and ask the user to approve, edit or drop it; for each approved one only, run `lesson promote --id <id> --to "${CLAUDE_PLUGIN_ROOT}/lessons/<stack>.jsonl"`. Then show the override counters of global lessons (`lesson list`) and, only if the user approves, run `lesson sync --to-dir "${CLAUDE_PLUGIN_ROOT}/lessons"` (add `--id <id>` per lesson to sync only some); it adds them to the global files and zeroes the synced rows. Committing those files in the plugin repo is the user's call. Flag lessons that recurred twice as needing enforcement. Then list every deviation from this procedure: agent not dispatched, improvisation, anything that blocked.

## Small-change lane
Decide from the actual diff, never from how small the request sounds. The lane applies only if the change touches at most 3 files and 100 lines and none of: migrations, schema, RLS, auth, permissions, sessions, env/secrets config (a change to `.pipeline-secrets-allow` included: it never takes this lane and always needs `security`), write paths for sensitive or financial data. Then skip the written plan and run: `dev` (commits on a worktree branch), `code-review`, `docs` only if an interface or setup step changed, `qa` (always: the `gate` requires it; with no tests for the area, `qa` verifies by hand and says so, which the `gate` scores as a coverage gap), then `gate` as in steps 5 and 6. The ledger applies unchanged (a single task, `--from` = base). There is no spec review: the lane excludes every domain that makes it required. If the diff exceeds any limit, switch to the full procedure.

## Rules
- Keep `.superpowers/` out of commits.
- Pass agents file paths (briefs, diffs, reports, ledger), not pasted content.
- Never fix findings yourself in the manager session; route them. The one exception is the spec in step 2, which this session wrote and corrects.
- Never edit the ledger, the lessons file or a generated brief by hand; use `ledger.py`, `package.py` and addenda files.
- Keep one progress record: the ledger. No `progress.md`, no second log.
