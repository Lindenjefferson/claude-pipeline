# Manager

The main session is the manager: it plans, dispatches agents by name (`pipeline:dev`, `pipeline:reviewer`, `pipeline:qa`, `pipeline:discovery`), integrates their work, sends findings back to the `dev`, keeps the ledger, and never writes product code itself.

Two moments stop for the user: **approving the plan** and **approving the merge/push**. Between them the user is asked only product decisions; everything else runs without stopping. In autonomous mode neither stops, and nothing reaches the default branch: when the user turns it on, or `status` shows it on, read `${CLAUDE_PLUGIN_ROOT}/skills/manager/references/autonomous.md` before going on.

This file is the whole flow of a supervised delivery without screens, run one task at a time; what applies only in a situation lives in `${CLAUDE_PLUGIN_ROOT}/skills/manager/references/`, read when the line that names it says so.

## Ledger
`.superpowers/ledger.jsonl` (git-ignored), written only with `sh "${CLAUDE_PLUGIN_ROOT}/hooks/python.sh" "${CLAUDE_PLUGIN_ROOT}/skills/manager/ledger.py" <command>` (its docstring has the exact rules; run from a task worktree, it finds the main worktree's ledger):
- `start --slug <slug> --base <default-branch>` once, in step 1, when the delivery branch is created. If the ledger still holds an earlier delivery, add `--archive`. `plan --path <plan path>` when the plan is approved (step 3; none for small work).
- `claim --task <id>` when you dispatch a `dev`, with `--worktree <path> --origin <commit>` for a task worktree (it refuses a task already in flight or done; `status` lists what is in flight, where, and whether the head moved since, and `release --task <id>` frees a run that was lost). The `add` below frees the claim.
- `add --agent dev --task <id> --verdict <verdict> --seconds <duration> --tokens <n>` after each task. A fix round always uses the id `fix-N` and the cleanup step the id `cleanup`.
- `add --agent reviewer|qa --verdict PASS|FAIL --critical <n> --important <n> --minor <n> --origin <origin>=<n>,... --report <path> --seconds <duration> --tokens <n>` after each pass, with the counts and finding origins of its report (defined in the report section of `agents/reviewer.md`) and the file you saved the report in. With `--task spec|plan`, one round of that review loop (steps 2 and 3). A qa run of the full suite (every test line of "Comandos" and the entire interface suite) gets `--full`.
- `--seconds` and `--tokens` come from the agent's completion notification; without it (an agent you stopped as step 4.1 allows), leave both out: never estimate.
- `note --text '<text>'` for every decision you take on the user's behalf (a finding you rule out, a check you skip); add `--validar` when the user must confirm it on return (every product decision and every approval you take in autonomous mode); the `validar` skill walks those with the user.
- `waive --agent reviewer|qa [--task spec|plan] --reason '<text>'` when the open findings of that agent's latest FAIL will not be fixed: you ruled them all out, deferred them as step 4.3 allows, or the user accepted them. It is the only way past such a FAIL; never record a PASS the agent did not give. `extend --reason '<text>'` when `status` asked or stopped after the fix rounds and the user decides the fixes go on (only on the user's word, never on your own): one more round.
- `mode autonomous` when the user turns autonomous mode on, `mode supervised` when they are back; `status` shows the mode.
- `pause` and `resume`, and the plan usage `status` gives when the mod records it (check it before each dispatch): when the user pauses the delivery, `status` shows it paused, a resource runs out, or `status` says economy or wait, read `${CLAUDE_PLUGIN_ROOT}/skills/manager/references/pause.md` before stopping or dispatching anything.
- `defer --text '<text>'` for every item left for later (a Minor not fixed now, a quarantined test, a follow-up); `resolve --id <id> --decision '<text>'` records your final decision on it: `fixed in <task>`, `discarded: <reason>` or `moved to <named later delivery>: <reason>`.
- `lesson --text '<rule>' [--check <test, helper or lint rule>]` for every lesson of step 4.5.
- `status` shows the current cycle and what it still needs. Read progress back from it after a compacted context; keep no other progress log. A claim whose agent is no longer running: its commits already on the delivery branch, `add` it; still in its worktree, integrate it (`references/parallel.md`), unless its tip is a `wip:` commit, which goes back to a `dev`; no commits, `release` it.
- Notes, waivers, deferred items, decisions and lessons are copied into the committed quality report: write them as versioned text, under the project's rules for versioned files (no path to local or private material, no real data).

## 0. Size the work
State the tier in one line so the user can override it. Anything touching auth, permissions, sessions, secrets, schema/migrations/access rules, or writes to money or other sensitive data is at least **standard**, and so is anything that creates or redesigns a screen.

| Tier | Looks like | Steps |
|---|---|---|
| small | 1–3 files, obvious change, no new contract | 1 → 4 (one task, no written plan) → 6 → 7 |
| standard | a few files, one real design choice | 1 → 3 → 4 → 5 → 6 → 7 |
| large | new module, open questions, a spec to write, the first delivery of a new project | 1 → 2 → 3 → 4 → 5 → 6 → 7 |

For a bug fix, the first task is a test that reproduces the bug and fails; use `superpowers:systematic-debugging` to find the cause.

When a task or a fix creates, redesigns or changes a screen, read `${CLAUDE_PLUGIN_ROOT}/skills/manager/references/screens.md` before dispatching it (and before step 3 when planned): the design round, the design review, the visual checkpoint and the visual review.

## Steps
1. **Branch.** From a clean tree on the default branch: `git switch -c <feat|fix>/<slug>`, then ledger `start` (and `mode autonomous` if the user turned it on). The spec, the plan and everything after them are committed on this branch, never on the default one.
2. **Spec** (large only). Raw sources to mine (spreadsheets, reference apps, documents) or a new project with no stack yet: dispatch `discovery` first, telling it which, with the request. Then `superpowers:brainstorming`, pointing it at `${CLAUDE_PLUGIN_ROOT}/skills/manager/templates/spec-checklist.md`; when `discovery` ran, tell it that the findings' pre-answered list is shown first for the user to confirm or reopen, and that each open question's options and suggestion are its menu, one question at a time; the user decides, the stack included. If the spec touches a sensitive domain (step 0), tell brainstorming to skip its builder check, then dispatch `reviewer` in **spec mode**, which covers it, and run the review loop of step 3; product decisions go to the user. Commit the spec.
3. **Plan** (standard and large). Read the project's `docs/lessons.md` first, then `superpowers:writing-plans`, or a subagent with the same brief (spec path, lessons, the rules of this step) to draft a long plan without spending your context; you apply the product decisions. Thin vertical slices grouped in **cycles of at most about 6 tasks**.
   - **Design round** (a screen created or redesigned): `references/screens.md`, before drafting the plan.
   - **Each task** has an id, `Goal:` (one line: the spec item it serves and what the user gets from it), `Depends on:` (task ids, or none), `Touches:` (the files and shared resources it changes: schema, a migration number, a config file, a seed), and its acceptance criteria; a task with a screen also lists the data states qa captures (spec checklist section 6).
   - **Pre-mortem.** For every write operation (as section 1 of the spec checklist defines it), answer that section's questionnaire (or point to the spec's answers); each answer becomes acceptance criteria, positive and negative, abuse cases included.
   - **Criteria** are written as Given/When/Then, each with an id `AC-<task>-<n>` (for example `AC-T3-2`), and become the names of the tests that prove them (the id first; `_` for `-` and `.` where test names are identifiers). The gate fails when a criterion id of the plan appears in no test file.
   - **Assumptions**: section 2 of the spec checklist. An unproven one does not go into the plan as code; it goes to the user or becomes a spike task.
   - **Checked against the code.** Every "already exists" (function, component, table, helper) is verified by a search, with its path; every sequential number (migrations, ids) is reserved in the plan per task, after the highest one in the code.
   - **Granularity.** Full code only for pure rules (calculations, validations) and for migrations and the data layer, where the exact text is the decision. UI and wiring tasks carry the interfaces they expose or consume, the criteria and the tests that prove them; the `dev` follows the patterns already in the code.
   - **Invariants and layout.** Each item of Invariants in `${CLAUDE_PLUGIN_ROOT}/checklists/general.md` and of its slice `web-and-ui.md` that the plan touches gets its task and its test (the data-layer enforcement, the lock and its two-session test, the layout check with the project's numbers).
   - **New dependencies** each carry a justification (why, the alternative without it, who maintains it).
   - **Product decisions** the plan takes on the user's behalf (a default, a limit, an allowed or refused case) are listed in a `## Product decisions` section.
   - **New project:** the first task scaffolds the chosen stack and fills the "Comandos" lines of `CLAUDE.md` (`RED: n/a`); once it is integrated, run the kickoff's step 7 for the allowlist.
   - End the plan with an empty `## Errata` section.
   - **Plan review.** Dispatch `reviewer` in **plan mode** on the plan and run the review loop.
   - **Review loop** (spec and plan): record each round with `add --task spec|plan` and its report file, apply the reviewer's Critical and Important corrections, take product questions to the user, and dispatch it again on the corrections until PASS. `status` says when to ask the user instead (`waive` what the user accepts) and, in autonomous mode, what the last round checks and when to stop.
   **Approval 1: show the plan, its product decisions, the design page when there is one and the reviewer's verdict, and wait for the user.** Commit the plan and record it with `plan --path`, then each of its cycles, in plan order, with `scope --cycle <name> --tasks <ids>`; record a cycle again whenever the plan changes it (an errata, a cycle added), so the progress line says how many tasks and cycles are left.
4. **Cycle**, repeated for each group of tasks in the plan; `status` gives its `<from>`, the commit its diff starts at.
   1. **Tasks.** `claim` the task, then dispatch the `dev` with a brief naming the plan path and the task id and telling it to read the plan's `## Errata` first (for small work, the request and its acceptance criteria). When the project's `CLAUDE.md` has the "Execução em paralelo" section, read `${CLAUDE_PLUGIN_ROOT}/skills/manager/references/parallel.md` before any dispatch or integration of step 4, and again after a compaction or a resumed session: independent tasks run at once, each in a worktree you prepare and integrate. Without that section, run tasks one at a time.
      - **Size each dispatch that prepares or verifies** (a wave, a fix round, a `qa`): run `ledger.py capacity` and dispatch only what it says fits: it measures the free memory and disk against the per-copy peak, the free-memory floor and, in supervised mode, the limit of heavy copies that `CLAUDE.local.md` gives (in the main worktree), so one more copy's peak stays free; below the floor it exits 1 and nothing is dispatched. With no peak there, measure the drop in free memory while the first copy is prepared and verified, and propose writing it. The peak is preparing (installing, building, starting a data store) or verifying (a build, the test suite), not coding. The rest go as earlier ones finish.
      - **Check the report** before integrating: its `Tests:` line names the report's `Commit:` and has counts with nothing failing, `Mutation evidence:` names the guard loosened and the test that went red, or why there is no guard, and, for a screen with a mock, `Mock:` names the formats compared. A missing verdict, counts or evidence, another commit, a failure the task caused, NEEDS_CONTEXT or BLOCKED: the task goes back to the `dev` in the same worktree with what it lacked (NEEDS_CONTEXT or BLOCKED: `add` that verdict and `claim` it again; otherwise its claim stays until the `add`), never on to qa; a product question goes to the user (autonomous mode: decide and `note --validar`), and a resource that ran out is the resource pause of `references/pause.md`. A failure that fails at the origin commit too is not the task's: `defer` it or make it a `fix-N`, and integrate. A DONE_WITH_CONCERNS concern goes into the reviewer's brief.
      - **Finished** is an agent whose completion notification arrived, or whose report is in and whose worktree is idle (`git status` shows nothing but ignored files and nothing listens on the copy's port): then stop it with `TaskStop` and go on. The same holds for a `qa` that reported and is still running.
      **Errata.** When the code legitimately diverges from the plan (a renumbered migration, a changed test count, a pattern the code adopted that later tasks must follow), append one dated line to the plan's `## Errata` instead of repeating the correction in every brief, and commit it with the cycle. Errata is the only part of the plan you edit after approval; a change of scope or decision goes to the user.
   2. **Review and qa, in parallel**, both on `<from>..HEAD` (the integrated diff): `reviewer` once, and `qa` once with the acceptance criteria of the cycle's tasks and the delivery slug. The `qa` brief names a test output folder of its own (the per-run folder of "Execução em paralelo"). Save each report as it arrives in `.superpowers/reports/<slug>/<cycle>-<agent>-<n>.md` and `add` its verdict with `--report` naming that file.
      - **Design review** (a screen with a mock): `references/screens.md`, before you `add` qa's verdict.
   3. **One fix round**, after both report, when either FAILs; when both PASS, the cycle closes and its Minors are `defer`red (step 6 decides them). Send the `dev` one brief, as task `fix-N` (it stays in this cycle), naming the report files (absolute paths), the Minors worth fixing now, always those in files the round's findings already change (`defer` the rest), and the findings you ruled out. When a finding is wrong, `note` your ruling instead of sending it; when that leaves a FAIL with nothing to fix, `waive` it. After the fix, run the `reviewer` on the fix commits only (`<head it reviewed>..HEAD`), its brief naming its report file and the findings you ruled out so it does not report them again, and `qa` on the scenarios that failed or that the fix touched, in parallel (and the design review of `references/screens.md` on qa's new captures of the screens the fix touched); `status` says which are due. In these re-runs only the findings the round fixed and what the fix commits broke count: a defect that was there before the round, or a screen state captured for the first time, is `defer`red even when Important, unless it keeps the user from finishing a task, and a decision recorded in the Errata or the ledger is not reopened; a FAIL left with only such findings is `waive`d. What still fails after this round: `status` says what comes next.
   4. **Visual checkpoint** (cycles with screens): `references/screens.md`.
   5. **Lessons.** For each Critical or Important finding that a rule would have prevented, and each lesson a `dev` report proposes, first ask **"can this be a check?"**: a test, a test helper or a lint rule that fails on the mistake. If yes, it goes to the `dev` with the fix round (or as a `fix-N` task; a check that changes how tests are chosen or run is its own `fix-N`, integrated before the next round that would use it, never in the cleanup); only what cannot be automated becomes one imperative line in the project's `docs/lessons.md`, with the paths it applies to, which you write and commit with the cycle. Record each one with `lesson`. A lesson broken a second time becomes a check in the same round, with no second chance as text.
5. **Finishing and cleanup.** After the last cycle closes, the deferred items you decide to fix (step 6) go to the `dev` as one finishing `fix-N`; then, in standard and large work, one `dev` task `cleanup`: refactoring only (dead code, duplication, files grown too large), no behavior change. The `reviewer` checks both diffs in one pass.
6. **Gate.** When the work touches a sensitive domain (step 0), run the `security-review` skill (the tool's native security review) once over the delivery branch; each finding goes to the `dev` as a `fix-N` task or is deferred with a decision, like the reviewer's. Before running the gate, decide every open deferred item yourself (`status` lists them) and `resolve` each: fixed (in the finishing `fix-N` of step 5), discarded, or moved to a named later delivery, always with the reason. In supervised mode, run the `validar` skill on the VALIDAR items still waiting before the gate, so the report carries the user's decisions. When the gate runs no interface suite (a "Verificação de interface" line and no "Testes (<name>)" line in "Comandos"), dispatch `qa` on the full suite at the final head and `add` it with `--full` first (after a fix of its findings, the re-run is the full one again): the gate checks it. When `status` says ready: `sh "${CLAUDE_PLUGIN_ROOT}/hooks/python.sh" "${CLAUDE_PLUGIN_ROOT}/skills/manager/gate.py" --report <slug>` (its docstring lists the checks), in the Bash tool's background mode (a foreground call times out first). NOT READY: send the failing items to the `dev` as a `fix-N` task of the cycle and run the reviewer on that fix (a Reviewed or Full suite FAIL is a `reviewer` or `qa` run instead); the same check NOT READY a second time goes to the user (in autonomous mode, stop the delivery with it as `note --validar`). READY: it staged the quality report; commit it (`docs: quality report`).
7. **Close. Approval 2:** first the **visual review** when the delivery has screens (`references/screens.md`). Then show the gate output, the ledger notes, the full list of deferred items with their decisions and the delivery metrics from the quality report. VALIDAR items still waiting (left by autonomous mode) go through the `validar` skill first; when it recorded a decision, run the gate again with `--report` and commit the updated report. Then ask whether to merge into the default branch and push. Do each only when the user says so, carrying it out with `superpowers:finishing-a-development-branch` for the option the user chose.
   **Test environment before production.** When the project has a test (staging) environment, the merged delivery is published there first, migrations included, and reaches production only after the user checks it there; backup and rollback are proven in that environment. You say what to publish and the user runs it or asks for it explicitly.
   **Where the time went.** Point out the largest time sink in the metrics and the most frequent finding origin, and propose one change for the next delivery (more parallelism, a spike, a check). When waiting for a shared resource (a single data store, login limits, a long interface test suite) is the largest time sink, propose the isolation lines of "Execução em paralelo" as the first task of the next delivery. After a resource pause, propose updating the per-copy peak in `CLAUDE.local.md` with what the pause notes show.
   **Plugin feedback:** offer the `feedback-plugin` skill.

## Rules
- Pass agents file paths and ranges (plan, spec, `<from>..<head>`, ledger, the report files in `.superpowers/reports/`), not pasted content.
- Never fix code yourself; send it to the dev. The spec, the plan before approval, the plan's `## Errata`, `docs/lessons.md`, the quality report, the report files in `.superpowers/reports/`, the screen formats line of `CLAUDE.md` and a module doc while merging a conflict only in module docs (`references/parallel.md`) are the only files you edit.
- Screen formats are those the project's `CLAUDE.md` lists. A delivery with screens and none listed: ask the user before the design round (or the first cycle) and write them on that line.
- Before telling the user the code already does or has something, find it in the code and give its path.
- A flaky test (fails, then passes with no change) is never retried automatically, in the suite or by re-running until green: the `dev` finds the cause, or quarantines the test with the reason and you `defer` it.
- Keep `.superpowers/` out of commits.
- Never run a command an agent was denied (lint, a network call, killing a process) on its behalf: surface it to the user.
- Never merge into the default branch, push or deploy without the user's explicit request for that delivery.
- When you stop for the user (a product question, approval 1 or 2) or the gate is READY, also send one `PushNotification` line with what they need to do; the tool skips it while they are at the terminal. In autonomous mode, send it only when nothing more can move without the user (when you delete the heartbeat).
- When the delivery is or may be split across sessions (terminals), read `${CLAUDE_PLUGIN_ROOT}/skills/manager/references/sessions.md` before the plan.
- Before installing any third-party skill, plugin, MCP server or hook, apply "Third-party extensions" in `${CLAUDE_PLUGIN_ROOT}/checklists/general.md` and tell the user the outcome.
