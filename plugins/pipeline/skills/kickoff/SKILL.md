# Project Kickoff

Prepares a project so the `pipeline` plugin's agents work from day one. It installs only the stack-agnostic structure; the stack setup is the project's to design. **Idempotent:** inspect first, add only what is missing, never overwrite an existing file, never commit or push.

## Steps (run from the project root)

1. **Pre-flight.** Confirm the plugin pieces exist: agents `pipeline:discovery`, `pipeline:dev`, `pipeline:reviewer` and `pipeline:qa` among the agent types, the skill `pipeline:manager` (with `ledger.py` and `gate.py` under `${CLAUDE_PLUGIN_ROOT}/skills/manager/`), `${CLAUDE_PLUGIN_ROOT}/hooks/pre-commit-secret-scan.py`, and the `superpowers` plugin enabled (`superpowers:brainstorming`, `writing-plans`, `systematic-debugging` and `finishing-a-development-branch` appear among the available skills; the pipeline depends on them). If any is missing, stop and tell the user; they belong to the plugin, do not recreate them here.
2. **Git.** `git init` if the folder is not a repo. Then ask the user before installing the native secret scan (one persistent git hook; if the permission system denies it, stop and report): `python "${CLAUDE_PLUGIN_ROOT}/hooks/pre-commit-secret-scan.py" --install-pre-commit`. git runs it on every commit and it blocks `.env`-style files and secret-looking lines in the index being committed; an existing pre-commit hook is kept as `pre-commit.pipeline-chained` and runs first, and a pre-push hook left by an older version of the plugin is removed. The hook stores no path: it finds the scanner through `CLAUDE_PIPELINE_HOME` or `git config pipeline.home` and blocks if neither resolves. If `git config --get pipeline.home` is empty, or names a folder that has no `hooks/pre-commit-secret-scan.py` (a clone that was moved or renamed leaves it stale, and then every commit is blocked), tell the user the command the installer prints (`git config --global pipeline.home ...`) and let them run it. Also tell the user the hook is client-side and `git commit --no-verify` skips it, so recommend enabling server-side push protection on the remote (GitHub: secret scanning push protection), and include that recommendation in the step 9 report.
3. **`.gitignore`.** Create from `templates/gitignore`, or append the template's missing blocks (with their comment headers). It must ignore `graphify-out/` (the graph is rebuilt locally, never committed), `.superpowers/`, `.env` and `.claude/settings.local.json`. Stack-specific ignores are the project's.
4. **Docs convention.** Create `docs/README.md` from `templates/docs-README.md` and `docs/lessons.md` from `templates/lessons.md` (skip each if present), and `docs/discovery/` and `docs/quality-reports/` with a `.gitkeep`. Per-module docs (`NN-*.md`) are not created now: the `dev` creates each one with the module's first task.
5. **`CLAUDE.md`.** Create from `templates/CLAUDE.md`, filling the project name and one-line description (ask the user if not obvious). If a `CLAUDE.md` exists, append only the sections and rules it lacks. The gate script runs the "Comandos" lines named Build, Typecheck, Lint, Testes and Auditoria, each written as a list item with the command between backticks (for example `- Testes:` followed by the test command in backticks), and searches the "Arquivos de teste" globs for acceptance-criterion ids; the `dev` uses the affected-tests line and the `dev` and `qa` the UI verification line. The plugin's `PreToolUse` hook reads the "Rodar em desenvolvimento" line (the dev server, command in backticks) and denies that command outside the Bash tool's background mode; with no command in backticks it does nothing, so leave the placeholder until the project has a dev server. Fill them from the project's own files (build scripts, task runner) as soon as the stack exists. The "Execução em paralelo" section stays a placeholder until the project knows how to run several copies at once; until then the `manager` runs tasks one at a time.
6. **The stack is the project's.** Kickoff installs no stack configuration, templates or rules. When the user scaffolds or configures the stack (now or later), check the current version and flags first, in the stack's package manager, `--help` and current docs, never from memory, and let the user and the project design the setup. Recommend that the project decide and record in its `CLAUDE.md`: the gate commands, the dependency audit included; a command that runs only the affected tests; a UI verification command when it has screens (a test environment with no dev tooling over the UI); closed-by-default data privileges with a test that sweeps them; how to run several copies at once ("Execução em paralelo"); a test environment before production. Re-run kickoff after scaffolding to fill "Comandos" and step 7.
7. **Command allowlist.** Keeps agents from being denied by the auto-mode classifier on routine commands. Use `templates/settings.allowlist.json`:
   - Every complete command in backticks in the `CLAUDE.md` "Comandos" section (no placeholder such as `<arquivo>`; the "Arquivos de teste" line holds globs, not a command, and is skipped) becomes one **exact** entry, `entry` with the command filled in. Never a prefix wildcard (`:*`): it would also allow commands added later and any arguments.
   - **Inspect each command's body before adding it**, not just its name: when it runs a project script or task (a package script, a make target, a local script file), read that body and every script it runs in turn, and refuse the command when any of them contains a `never_allow` term (case-insensitive, whole words). List every refused command and the term that matched in the report to the user.
   - Add the template's `deny` entries to `permissions.deny`: only the user edits `.pipeline-secrets-allow`, the secret scan's allowlist, and agents may not skip the hook with `git commit --no-verify`/`-n`, run `sudo`, force-push or `chmod 777`.
   Merge into the project `.claude/settings.json` (shared, committed; personal entries go in `.claude/settings.local.json`): parse the existing file, append missing entries to `permissions.allow` and `permissions.deny` keeping order and every existing key (`ask`, `hooks`, `env`...), never remove or reorder, never overwrite the file. If it does not parse, stop and report. **Show the user the diff and ask before writing**; if the permission system denies the write, stop and report (never route around it). Empty "Comandos": add only the `deny` entries and say so. The entries are exact, so **re-run kickoff whenever the commands or the scripts behind them change**: a changed body is inspected again, and an entry that now fails the check is reported to the user for removal (kickoff never removes entries itself).
8. **Knowledge graph.** Only when raw sources or code already exist; otherwise skip and tell the user to run this step after `discovery` gathers them. A corpus of only a few small files gains little from a graph: say so and skip until the sources grow. Already partly set up? Skip 8.1 if `graphify-out/graph.json` exists, skip 8.3 if `CLAUDE.md` already has the graphify section and `.claude/settings.json` has its hooks, skip 8.4 if `.git/hooks/post-commit` exists, and always run 8.5, 8.6 and step 9.
   1. Build: `/graphify .` (first build uses the LLM on docs/papers; confirm with the user when the corpus is large).
   2. **Ask the user before 8.3 and 8.4.** They install persistent hooks (project `.claude/settings.json` hooks, a `CLAUDE.md` section, git post-commit/post-checkout hooks), which the permission system may deny. If it denies, stop and report; never write those hooks by hand to get around it.
   3. `python -m graphify claude install` (graphify section in `CLAUDE.md` and PreToolUse hooks in the project `.claude/settings.json`).
   4. `python -m graphify hook install` (git hooks keep the graph fresh after commits, AST-only).
   5. Fix-ups, after 8.3 and 8.4. If `which graphify` finds nothing, make the commands use `python -m graphify`; because the graph is git-ignored, drop the merge driver:
      ```bash
      sed -i -E 's/(^|[^m] )graphify (query|path|explain|update)/\1python -m graphify \2/g; s/`graphify (query|path|explain|update)/`python -m graphify \1/g' CLAUDE.md
      sed -i -E 's/"command": "graphify /"command": "python -m graphify /' .claude/settings.json
      sed -i '/graphify-out\/graph.json merge=graphify/d' .gitattributes; [ -s .gitattributes ] || rm .gitattributes
      git config --local --unset-all merge.graphify.name; git config --local --unset-all merge.graphify.driver
      ```
   6. **Noisy graphify hook (old installs).** Read `.claude/settings.json` and parse it as JSON; if it does not parse, stop and tell the user (never `sed` it). Look in `hooks.PreToolUse` for entries whose `matcher` contains `Bash` and whose command contains `graphify` but not `hook-guard`: that is the old inline hook, which injects a "MANDATORY: run graphify" reminder on almost every Bash call. If there are none, do nothing (current graphify guards itself). Otherwise show the user a diff that sets those entries' `matcher` to `Read|Grep|Glob` (this drops the Bash search nudge; `python -m graphify claude install` is the alternative that rewrites them to the current guards) and ask for confirmation. After a yes, write the file back with `json.dump(..., indent=2, ensure_ascii=False)`, keeping every other key and entry, parse it again to verify and show `git diff`. Touch no entry that is not graphify's. If a permission denies the edit, stop and report.
9. **Verify with evidence**, then report each result: the plugin is enabled for this repo (`claude plugin list` shows `pipeline@linden-plugins` enabled); `git check-ignore graphify-out/graph.json` prints the path; `git status` shows only intended new files; if step 2 installed it, `.git/hooks/pre-commit` contains `secretscan-managed` (`grep -l secretscan-managed .git/hooks/pre-commit`; with `core.hooksPath` set, look in the folder `git rev-parse --git-path hooks` prints), and say whether a previous pre-commit hook was chained; then run that hook once with nothing staged (`sh "$(git rev-parse --git-path hooks)/pre-commit"`): exit 0 means the scanner resolves, and "secret scanner not found" means `pipeline.home` is wrong, so report that every commit is blocked until the user fixes it. Run this check also when step 2 did not install the hook but one is already there. If 8.3 and 8.4 ran, also: `.claude/settings.json` parses as JSON and its hook commands start with `python -m graphify`; `python -m graphify --help` exits 0; `git config --local --get-regexp merge` prints nothing. If they did not run, say so. When the project already had a `.claude/settings.json` or `.claude/settings.local.json`, also report, read-only and without changing anything, any `env` entry that sets a `*_BASE_URL` or a proxy, `enableAllProjectMcpServers`, and any hook whose command is not the pipeline's or graphify's, so the user sees what the repository runs on their machine. If step 7 ran: `.claude/settings.json` parses, `permissions.allow` holds the new entries plus every entry it had before and none of the new ones ends in `:*`, and `permissions.deny` holds every `deny` entry of the template.
10. **Hand off.** State the flow and ask whether to start now: the `manager` sizes each request (small, standard, large), writes a spec for large work (with `discovery` when there are raw sources, and one `reviewer` pass on specs that touch sensitive domains), a plan the `reviewer` checks and the user approves, then cycles of a few tasks: `dev` per task (independent ones in parallel), one `reviewer` and one `qa` pass per cycle at the same time and one fix round; at the end `gate.py` checks the ledger and the criteria traced to tests and runs build, types, lint, tests, the dependency audit and the secret scan locally. Merge and push happen only when the user approves.

## Notes
- The plugin is enabled per repo (`--scope local`), never globally, so repos that do not enable it never load the agents, skills or hook. Enabling the plugin is the only per-project switch.
- Every template is project- and stack-agnostic. Stack rules (data access, test policy, deploy target, UI conventions) belong in the project's own `CLAUDE.md` and `docs/lessons.md` after brainstorming decides them.
- graphify's hooks are another plugin's config: step 8.6 touches them only for the old noisy form, and only after the user confirms.
