# Project Kickoff

Prepares a project so the `pipeline` plugin's agents work from day one. **Idempotent:** inspect first, add only what is missing, never overwrite an existing file, never commit or push.

## Steps (run from the project root)

1. **Pre-flight.** Confirm the plugin pieces exist: agents `pipeline:discovery`, `pipeline:dev`, `pipeline:reviewer`, `pipeline:qa` and `pipeline:gate` among the agent types, the skill `pipeline:manager` (with `ledger.py` under `${CLAUDE_PLUGIN_ROOT}/skills/manager/`), `${CLAUDE_PLUGIN_ROOT}/hooks/pre-commit-secret-scan.py`, and the `superpowers` plugin enabled (`superpowers:brainstorming`, `writing-plans`, `systematic-debugging` and `finishing-a-development-branch` appear among the available skills; the pipeline depends on them). If any is missing, stop and tell the user; they belong to the plugin, do not recreate them here.
2. **Git.** `git init` if the folder is not a repo. Then ask the user before installing the native secret scan (one persistent git hook; if the permission system denies it, stop and report): `python "${CLAUDE_PLUGIN_ROOT}/hooks/pre-commit-secret-scan.py" --install-pre-commit`. git runs it on every commit and it blocks `.env`-style files and secret-looking lines in the index being committed; an existing pre-commit hook is kept as `pre-commit.pipeline-chained` and runs first, and a pre-push hook left by an older version of the plugin is removed. The hook stores no path: it finds the scanner through `CLAUDE_PIPELINE_HOME` or `git config pipeline.home` and blocks if neither resolves. If `git config --get pipeline.home` is empty, tell the user the command the installer prints (`git config --global pipeline.home ...`) and let them run it. Also tell the user the hook is client-side and `git commit --no-verify` skips it, so recommend enabling server-side push protection on the remote (GitHub: secret scanning push protection), and include that recommendation in the step 10 report.
3. **Stack detection.** Decides which add-ons apply; core (every other step) always runs. Detect from files, never assume:
   - **nextjs**: `package.json` has `next` in `dependencies`/`devDependencies` (major version from the installed `node_modules/next/package.json`, else the range).
   - **supabase**: a `supabase/` folder (`supabase/config.toml`) or any `@supabase/*` / `supabase` package.
   - Package manager from the lockfile (`package-lock.json` npm, `pnpm-lock.yaml` pnpm, `yarn.lock` yarn, `bun.lock*` bun); templates use npm, translate them.
   Report what was detected. No stack yet (new project): apply core only and tell the user to run `kickoff` again after scaffolding; it is idempotent and adds only the add-ons. Add-ons load only when detected, which keeps agent context small.
4. **`.gitignore`.** Create from `templates/gitignore`, or append the template's missing blocks (with their comment headers). It must ignore `graphify-out/` (the graph is rebuilt locally, never committed), `.env` and `.claude/settings.local.json`. Per detected add-on, append the missing lines of `templates/nextjs/gitignore` (its `# playwright` block only when the project has Playwright or step 8 adds it) and `templates/supabase/gitignore` (`*.types.tmp` is the temp file of an atomic `db:types` script: generate to `*.types.tmp`, then rename, so a failed run never truncates the types file).
5. **Docs convention.** Create `docs/README.md` from `templates/docs-README.md` (skip if present), and `docs/discovery/` and `docs/quality-reports/` with a `.gitkeep`. Per-module docs (`NN-*.md`) are not created now: the `dev` creates each one with the module's first task.
6. **`CLAUDE.md`.** Create from `templates/CLAUDE.md`, filling the project name and one-line description (ask the user if not obvious). If a `CLAUDE.md` exists, append only the sections it lacks.
7. **Command allowlist.** Keeps agents from being denied by the auto-mode classifier on routine commands (seen: `npm run lint` denied to `dev` as "Security Weaken"). Use `templates/settings.allowlist.json`; `core` always, `nextjs`/`supabase` only when detected:
   - Fixed entries: the stack's list, only those whose binary exists.
   - Scripts: every `package.json` script whose name matches the stack's `script_name_globs` (and each script named in the `CLAUDE.md` "Comandos" section) becomes one **exact** entry, `script_entry` with the name filled in (`Bash(npm run db:types)`; the `test` script also gets `Bash(npm test)`). Never a prefix wildcard such as `Bash(npm run db:*)`: it would also allow scripts added later and any arguments (`--linked`, `--db-url`). The only prefix entry is the template's `migration new:*`, which only writes a local file.
   - **Inspect each script's body before adding it**, not just its name: read the command string in `package.json`, follow every script it runs (`npm run x`, `pnpm x`, `run-s`/`run-p`/`concurrently` targets) and any local script file it executes, and refuse the script when any of them contains a `never_allow` term (case-insensitive, whole words: `db push`, `db dump`, `--linked`, `--db-url`, `link`, `migration repair`, `secrets set`, `deploy`, `vercel`, `git push`, `rm -rf`). List every refused script and the term that matched in the report to the user.
   - Translate `npm` to the detected package manager. Never add a bare wildcard like `Bash(npm:*)`.
   - Add the template's `deny` entries to `permissions.deny`: only the user edits `.pipeline-secrets-allow`, the secret scan's allowlist, and agents may not skip the hook with `git commit --no-verify`/`-n`.
   Merge into the project `.claude/settings.json` (shared, committed; personal entries go in `.claude/settings.local.json`): parse the existing file, append missing entries to `permissions.allow` and `permissions.deny` keeping order and every existing key (`ask`, `hooks`, `env`...), never remove or reorder, never overwrite the file. If it does not parse, stop and report. **Show the user the diff and ask before writing**; if the permission system denies the write, stop and report (never route around it). Empty "Comandos" section and no scripts: add only the `deny` entries and say so. The entries are exact, so **re-run kickoff whenever `package.json` scripts are added or changed**: a changed body is inspected again, and an entry whose script now fails the check is reported to the user for removal (kickoff never removes entries itself).
8. **Stack add-ons** (only for what step 3 detected; each asks the user first and never overwrites an existing file).
   - **Check current versions first.** Before writing or fixing any scaffold/install command (here, in a spec or in a plan), check the current version and flags: `npm view <pkg> version`, the package's current docs, `npx <cli> --help`. Never write versions or flags from memory (seen: Next 16 renamed `middleware.ts` to `proxy.ts`, shadcn 4 dropped `--base-color`, vitest 5 needs `@types/node` 22). Add this rule to the project `CLAUDE.md` "Regras que valem sempre" if missing.
   - **nextjs (Next >= 16):** `next.config.*` sets `agentRules: false` (from Next 16, `next dev` writes an agent-rules block into `CLAUDE.md`; that file belongs to the pipeline). No config yet: create `next.config.ts` from `templates/nextjs/next.config.ts`; else add the key to the existing config object. Record in `CLAUDE.md` that request interception lives in `proxy.ts` (not `middleware.ts`) so plans and briefs use the right name. Mobile-first project (style guide or spec says so; ask if unsure) with shadcn (`components.json`): apply `templates/nextjs/touch-targets.md` to the primitives in `components/ui/`, and add to `CLAUDE.md` that every primitive added later gets the same 44px treatment. **Browser checks through the project's own Playwright** (skip if `@playwright/test` is already a dependency and an `e2e:smoke` script exists). Propose, as one diff shown to the user for approval the way step 7 shows the allowlist: `@playwright/test` as a devDependency at the version `npm view @playwright/test version` prints, and the script `"e2e:smoke": "playwright test --grep @smoke"` (both in `templates/nextjs/playwright.package.json`); `playwright.config.ts` from `templates/nextjs/playwright.config.ts` (tests in `e2e/`, Chromium only; its `webServer` runs `npm run dev` with `reuseExistingServer: true`, so Playwright reuses a server already on the URL and stops only one it started, and `E2E_BASE_URL=<url>` skips `webServer` entirely to test a `next dev` already running on another port); `e2e/smoke.spec.ts` from `templates/nextjs/e2e/smoke.spec.ts`; and the `# playwright` block of `templates/nextjs/gitignore`. Never overwrite an existing config or spec. On approval, add the dependency with the package manager (`npm install -D @playwright/test@<version>`, which also updates the lockfile), then write the script and the files. Tell the user to run `npx playwright install chromium` once per machine (it downloads the browser; ask before running it yourself). Add the exact allowlist entry `Bash(npm run e2e:smoke)` through step 7 (same body inspection, same diff); never `Bash(npx playwright:*)` or another prefix. Add to the `CLAUDE.md` "Comandos" section the line `Verificação no navegador: npm run e2e:smoke (Playwright do projeto; specs em e2e/, os de fumaça marcados @smoke; npx playwright test <arquivo> para um spec; E2E_BASE_URL=<url> reaproveita um next dev já rodando noutra porta). Checagem ad hoc: script Playwright numa pasta temporária fora do projeto`. If the user declines, add nothing to the project and add instead the line `Verificação no navegador: script Playwright numa pasta temporária fora do projeto (npm install playwright lá; npx playwright install chromium só se faltar o Chromium do cache; node <pasta>/check.mjs abre, age, verifica e sai); reusar o next dev que já serve a pasta, ou subir em background e parar no fim`: the `dev` and `qa` agents carry that procedure.
   - **supabase:** copy `templates/supabase/0000_privilegios_base.sql` to `supabase/migrations/` (revokes `anon` on tables/views, `truncate`/`references`/`trigger`/`maintain` from `authenticated`, sequences from both, `execute` on functions, plus the default privileges for future objects). New project: name it to sort first (`0000_...`, or the earliest timestamp if the project uses timestamps). Existing project: add it as the next numbered migration, never edit an applied one; if a table is meant to be readable by `anon`, stop and ask. Copy `templates/supabase/tests/00_privilegios_sweep.sql` to `supabase/tests/`: a pgTAP sweep of effective privileges (`has_function_privilege`, so `EXECUTE` inherited from `PUBLIC` counts) against an exact-signature allowlist (`ALLOWLIST` marker; every client-callable function goes there as `public.fn(arg types)`, never by name), plus RLS on every table, no `anon` table grants, read-only views that all run as the caller (`security_invoker=true`), no `anon`/`authenticated` privilege on materialized views or foreign tables (RLS does not apply to them) and no sequence privileges, over the schemas listed next to the `ALLOWLIST` marker (default `public`; add every schema the API exposes, and repeat the base migration's revokes for it). Record in `CLAUDE.md`: each function migration revokes `execute` from `public, anon, authenticated` and grants only what the allowlist lists; each view is created `with (security_invoker = true)` and gets the write revoke; each materialized view or foreign table revokes all from `anon, authenticated` (read it through a function or a `security_invoker` view instead); keys are `uuid` or `identity` (a `serial` default needs sequence privileges the sweep forbids). `MAINTAIN` exists only on Postgres >= 17: on older servers drop it from both files. Suggest adding the sweep's run command (e.g. `npm run db:test`) to "Comandos" if missing.
9. **Knowledge graph.** Only when raw sources or code already exist; otherwise skip and tell the user to run this step after `discovery` gathers them. A corpus of only a few small files gains little from a graph: say so and skip until the sources grow. Already partly set up? Skip 9.1 if `graphify-out/graph.json` exists, skip 9.3 if `CLAUDE.md` already has the graphify section and `.claude/settings.json` has its hooks, skip 9.4 if `.git/hooks/post-commit` exists, and always run 9.5 and step 10.
   1. Build: `/graphify .` (first build uses the LLM on docs/papers; confirm with the user when the corpus is large).
   2. **Ask the user before 9.3 and 9.4.** They install persistent hooks (project `.claude/settings.json` hooks, a `CLAUDE.md` section, git post-commit/post-checkout hooks), which the permission system may deny. If it denies, stop and report; never write those hooks by hand to get around it.
   3. `python -m graphify claude install` (graphify section in `CLAUDE.md` and PreToolUse hooks in the project `.claude/settings.json`).
   4. `python -m graphify hook install` (git hooks keep the graph fresh after commits, AST-only).
   5. Fix-ups, after 9.3 and 9.4. If `which graphify` finds nothing, make the commands use `python -m graphify`; because the graph is git-ignored, drop the merge driver:
      ```bash
      sed -i -E 's/(^|[^m] )graphify (query|path|explain|update)/\1python -m graphify \2/g; s/`graphify (query|path|explain|update)/`python -m graphify \1/g' CLAUDE.md
      sed -i -E 's/"command": "graphify /"command": "python -m graphify /' .claude/settings.json
      sed -i '/graphify-out\/graph.json merge=graphify/d' .gitattributes; [ -s .gitattributes ] || rm .gitattributes
      git config --local --unset-all merge.graphify.name; git config --local --unset-all merge.graphify.driver
      ```
10. **Verify with evidence**, then report each result: the plugin is enabled for this repo (`claude plugin list` shows `pipeline@linden-plugins` enabled); `git check-ignore graphify-out/graph.json` prints the path; `git status` shows only intended new files; if step 2 installed it, `.git/hooks/pre-commit` contains `secretscan-managed` (`grep -l secretscan-managed .git/hooks/pre-commit`; with `core.hooksPath` set, look in the folder `git rev-parse --git-path hooks` prints), and say whether a previous pre-commit hook was chained. Record it in the report to the user (hook installed or why not). If 9.3 and 9.4 ran, also: `.claude/settings.json` parses as JSON and its hook commands start with `python -m graphify`; `python -m graphify --help` exits 0; `git config --local --get-regexp merge` prints nothing. If they did not run, say so. If step 7 ran: `.claude/settings.json` parses, `permissions.allow` holds the new entries plus every entry it had before and none of them ends in `:*` except `migration new:*`, and `permissions.deny` holds every `deny` entry of the template. If step 8 ran: `next.config.*` contains `agentRules: false`; if Playwright was added, `npx playwright test --list` exits 0 and lists the `@smoke` spec, and `permissions.allow` holds `Bash(npm run e2e:smoke)`; with Supabase running locally (`npx supabase status`), the sweep passes after `npx supabase db reset` (ask first: it wipes the local database).
11. **Hand off.** State the flow and ask whether to start now: the `manager` sizes each request (small, standard, large), writes a spec for large work (with `discovery` when there are raw sources, and one `reviewer` pass on specs that touch sensitive domains), a plan the user approves, then per task `dev` → `reviewer` → `qa`, and at the end the `gate` runs build, types, lint, tests and the secret scan locally. Merge and push happen only when the user approves.

## Notes
- The plugin is enabled per repo (`--scope local`), never globally, so repos that do not enable it never load the agents, skills or hook. Enabling the plugin is the only per-project switch.
- Everything a template contains is project-agnostic. Stack rules (ORM choice, test policy, deploy target) belong in the project's own `CLAUDE.md` after brainstorming decides them; the add-ons in step 8 are only the conventions every project on that stack needs.
- Context budget: core is always installed; stack add-ons and their `CLAUDE.md` lines are added only when step 3 detects the stack, never "just in case".
- graphify's PreToolUse hook (another plugin) injects a "MANDATORY: run graphify" reminder on almost every Bash call, including ledger and git commands. It is noise for the pipeline agents; kickoff does not change it. If the user wants less noise, they can narrow that hook's matcher to `Read|Grep|Glob` in `.claude/settings.json` (their call: it is another plugin's config).
