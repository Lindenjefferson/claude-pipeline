# Project Kickoff

Prepares a project so the `pipeline` plugin's agents work from day one. **Idempotent:** inspect first, add only what is missing, never overwrite an existing file, never commit or push.

## Steps (run from the project root)

1. **Pre-flight.** Confirm the plugin pieces exist: agents `pipeline:discovery`, `pipeline:dev`, `pipeline:db`, `pipeline:security`, `pipeline:audit`, `pipeline:design`, `pipeline:code-review`, `pipeline:qa`, `pipeline:gate` and `pipeline:docs` among the agent types, the skill `pipeline:manager` (with `ledger.py` and `package.py` under `${CLAUDE_PLUGIN_ROOT}/skills/manager/`), and `${CLAUDE_PLUGIN_ROOT}/hooks/pre-commit-secret-scan.py` (the plugin's `hooks/hooks.json` wires it while the plugin is enabled), and the `superpowers` plugin enabled (`superpowers:brainstorming`, `writing-plans`, `using-git-worktrees`, `finishing-a-development-branch` appear among the available skills; the pipeline depends on them). If any is missing, stop and tell the user; they belong to the plugin, do not recreate them here.
2. **Git.** `git init` if the folder is not a repo. Then ask the user before installing the push-time secret scan (a persistent git hook; if the permission system denies it, stop and report): `python "${CLAUDE_PLUGIN_ROOT}/hooks/pre-commit-secret-scan.py" --install-pre-push`. It never overwrites an existing pre-push hook. The hook stores no path: it finds the scanner through `CLAUDE_PIPELINE_HOME` or `git config pipeline.home` and blocks the push if neither resolves. If `git config --get pipeline.home` is empty, tell the user the command the installer prints (`git config --global pipeline.home ...`) and let them run it. Unlike the Claude Code hook, it blocks a push of secret-containing commits however git is invoked.
3. **Stack detection.** Decides which add-ons apply; core (every other step) always runs. Detect from files, never assume:
   - **nextjs**: `package.json` has `next` in `dependencies`/`devDependencies` (major version from the installed `node_modules/next/package.json`, else the range).
   - **supabase**: a `supabase/` folder (`supabase/config.toml`) or any `@supabase/*` / `supabase` package.
   - Package manager from the lockfile (`package-lock.json` npm, `pnpm-lock.yaml` pnpm, `yarn.lock` yarn, `bun.lock*` bun); templates use npm, translate them.
   Report what was detected. No stack yet (new project): apply core only and tell the user to run `kickoff` again after scaffolding; it is idempotent and adds only the add-ons. Add-ons load only when detected, which keeps agent context small.
4. **`.gitignore`.** Create from `templates/gitignore`, or append the template's missing blocks (with their comment headers). It must ignore `graphify-out/` (the graph is rebuilt locally, never committed), `.env` and `.claude/settings.local.json`. Per detected add-on, append the missing lines of `templates/nextjs/gitignore` and `templates/supabase/gitignore` (`*.types.tmp` is the temp file of an atomic `db:types` script: generate to `*.types.tmp`, then rename, so a failed run never truncates the types file).
5. **Docs convention.** Create `docs/README.md` from `templates/docs-README.md` (skip if present), and `docs/discovery/` and `docs/quality-reports/` with a `.gitkeep` (its presence turns on the plugin's push gate for this project). Per-module docs (`NN-*.md`) are not created now: once a spec exists, dispatch the `docs` agent to create them.
6. **`CLAUDE.md`.** Create from `templates/CLAUDE.md`, filling the project name and one-line description (ask the user if not obvious). If a `CLAUDE.md` exists, append only the sections it lacks.
7. **Command allowlist.** Keeps agents from being denied by the auto-mode classifier on routine commands (seen: `npm run lint` denied to `dev` as "Security Weaken"). Build the candidate list from the `CLAUDE.md` "Comandos" section and the `package.json` scripts, using `templates/settings.allowlist.json`: `core` always, `nextjs`/`supabase` only when detected, and only entries whose script or binary exists. Translate `npm` to the detected package manager. Never add anything from `never_allow` (remote or destructive: `db push`, `link`, deploys, `git push`, `rm -rf`) or a bare wildcard like `Bash(npm:*)`.
   Merge into the project `.claude/settings.json` (shared, committed; personal entries go in `.claude/settings.local.json`): parse the existing file, append missing entries to `permissions.allow` keeping order and every existing key (`deny`, `ask`, `hooks`, `env`...), never remove or reorder, never overwrite the file. If it does not parse, stop and report. **Show the user the diff and ask before writing**; if the permission system denies the write, stop and report (never route around it). Empty "Comandos" section and no scripts: skip and say so.
8. **Stack add-ons** (only for what step 3 detected; each asks the user first and never overwrites an existing file).
   - **Check current versions first.** Before writing or fixing any scaffold/install command (here, in a spec or in a plan), check the current version and flags: `npm view <pkg> version`, the package's current docs, `npx <cli> --help`. Never write versions or flags from memory (seen: Next 16 renamed `middleware.ts` to `proxy.ts`, shadcn 4 dropped `--base-color`, vitest 5 needs `@types/node` 22). Add this rule to the project `CLAUDE.md` "Regras que valem sempre" if missing.
   - **nextjs (Next >= 16):** `next.config.*` sets `agentRules: false` (from Next 16, `next dev` writes an agent-rules block into `CLAUDE.md`; that file belongs to the pipeline). No config yet: create `next.config.ts` from `templates/nextjs/next.config.ts`; else add the key to the existing config object. Record in `CLAUDE.md` that request interception lives in `proxy.ts` (not `middleware.ts`) so plans and briefs use the right name. Mobile-first project (style guide or spec says so; ask if unsure) with shadcn (`components.json`): apply `templates/nextjs/touch-targets.md` to the primitives in `components/ui/`, and add to `CLAUDE.md` that every primitive added later gets the same 44px treatment.
   - **supabase:** copy `templates/supabase/0000_privilegios_base.sql` to `supabase/migrations/` (revokes `anon` on tables/views, `truncate`/`references`/`trigger`/`maintain` from `authenticated`, sequences from both, `execute` on functions, plus the default privileges for future objects). New project: name it to sort first (`0000_...`, or the earliest timestamp if the project uses timestamps). Existing project: add it as the next numbered migration, never edit an applied one; if a table is meant to be readable by `anon`, stop and ask. Copy `templates/supabase/tests/00_privilegios_sweep.sql` to `supabase/tests/`: a pgTAP sweep of effective privileges (`has_function_privilege`, so `EXECUTE` inherited from `PUBLIC` counts) against an exact-signature allowlist (`ALLOWLIST` marker; every client-callable function goes there as `public.fn(arg types)`, never by name), plus RLS on every public table, no `anon` table grants, read-only views and no sequence privileges. Record in `CLAUDE.md`: each function migration revokes `execute` from `public, anon, authenticated` and grants only what the allowlist lists; each view is created `with (security_invoker = true)` and gets the write revoke; keys are `uuid` or `identity` (a `serial` default needs sequence privileges the sweep forbids). `MAINTAIN` exists only on Postgres >= 17: on older servers drop it from both files. Suggest adding the sweep's run command (e.g. `npm run db:test`) to "Comandos" if missing.
9. **Knowledge graph.** Only when raw sources or code already exist; otherwise skip and tell the user to run this step after `discovery` gathers them. A corpus of only a few small files gains little from a graph: say so and skip until the sources grow. Already partly set up? Skip 9.1 if `graphify-out/graph.json` exists, skip 9.3 if `CLAUDE.md` already has the graphify section and `.claude/settings.json` has its hooks, skip 9.4 if `.git/hooks/post-commit` exists, and always run 9.5 and step 10.
   1. Build: `/graphify .` (first build uses the LLM on docs/papers; confirm with the user when the corpus is large).
   2. **Ask the user before 9.3 and 9.4.** They install persistent hooks (project `.claude/settings.json` hooks, a `CLAUDE.md` section, git post-commit/post-checkout hooks), which the permission system may deny. If it denies, stop and report; never write those hooks by hand to get around it.
   3. `python -m graphify claude install` (graphify section in `CLAUDE.md` and PreToolUse hooks in the project `.claude/settings.json`).
   4. `python -m graphify hook install` (git hooks keep the graph fresh after commits, AST-only).
   5. Fix-ups, after 9.3 and 9.4. If `which graphify` finds nothing, make the commands use `python -m graphify`; because the graph is git-ignored, drop the merge driver:
      ```bash
      sed -i -E 's/(^|[^m] )graphify (query|path|explain|update)/\1python -m graphify \2/g; s/`graphify (query|path|explain|update)/`python -m graphify \1/g' CLAUDE.md
      sed -i -E 's/"command": "graphify /"command": "python -m graphify /' .claude/settings.json
      sed -i '/graphify-out\/graph.json merge=graphify/d' .gitattributes; [ -s .gitattributes ] || rm .gitattributes
      git config --local --unset-all merge.graphify.name; git config --local --unset-all merge.graphify.driver
      ```
10. **Verify with evidence**, then report each result: the plugin is enabled for this repo (`claude plugin list` shows `pipeline@linden-plugins` enabled); `git check-ignore graphify-out/graph.json` prints the path; `git status` shows only intended new files; if step 2 installed it, `.git/hooks/pre-push` contains `secretscan-managed`. If 9.3 and 9.4 ran, also: `.claude/settings.json` parses as JSON and its hook commands start with `python -m graphify`; `python -m graphify --help` exits 0; `git config --local --get-regexp merge` prints nothing. If they did not run, say so. If step 7 ran: `.claude/settings.json` parses and `permissions.allow` holds the new entries plus every entry it had before. If step 8 ran: `next.config.*` contains `agentRules: false`; with Supabase running locally (`npx supabase status`), the sweep passes after `npx supabase db reset` (ask first: it wipes the local database).
11. **Hand off.** State the pipeline and ask whether to start `discovery` now: discovery → brainstorming → spec review → writing-plans → dev/db → docs + reviewers → gate (quality report). In the spec review the reviewers read the approved spec before any code and the spec is corrected until they pass; it is required when the spec touches auth, permissions, RLS, schema/migrations, secrets or sensitive/financial data. The `manager` skill runs everything from the spec review onward and keeps the ledger that syncs the agents. The `manager` creates each delivery worktree from the module branch (where the spec and plan live), not from the default branch; the `manager` skill owns the details.

## Notes
- The plugin is enabled per repo (`--scope local`), never globally, so repos that do not enable it never load the agents, skills or hook. Enabling the plugin is the only per-project switch.
- Everything a template contains is project-agnostic. Stack rules (ORM choice, test policy, deploy target) belong in the project's own `CLAUDE.md` after brainstorming decides them; the add-ons in step 8 are only the conventions every project on that stack needs.
- Context budget: core is always installed; stack add-ons and their `CLAUDE.md` lines are added only when step 3 detects the stack, never "just in case".
- graphify's PreToolUse hook (another plugin) injects a "MANDATORY: run graphify" reminder on almost every Bash call, including ledger and git commands. It is noise for the pipeline agents; kickoff does not change it. If the user wants less noise, they can narrow that hook's matcher to `Read|Grep|Glob` in `.claude/settings.json` (their call: it is another plugin's config).
